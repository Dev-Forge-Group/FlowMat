# 주간 개발 계획 (2026-10-19 ~ 10-23)

작성: 2026-10-17, 리드. 기준은 그날 작업 트리와 [WORKBOARD](WORKBOARD.md)다. 일이 끝나거나 바뀌면 여기 표시하고, 끝난 일은 WORKBOARD §2에도 적는다.

## 시작 상태

- 2eh–2el(Split, 손실률, 지연, 설비 동시 작업 수, 생산 실행의 공정 단계)은 로컬 검증까지 끝났다. 전체 백엔드 1,460건이 통과했다.
- 커밋 전 마이그레이션이 넷이다. V88(Join), V89(Split), V90(설비 동시 작업 수), V91(지침 단계의 공정). 개발 DB 5434는 V87이다.
- 개발 DB 컨테이너 `flowmat-session1-db`가 10-17 낮부터 멈춰 있다(Exited 0). 누가 멈췄는지는 모른다.
- 모듈 경계 단계 B는 105곳 중 48곳이 남았다. inventory → catalog 14곳, production → catalog 7곳, quality → catalog 5곳이 크다.
- 문서 문체 정리는 `domain/equipment.md` 한 파일만 했다.

## 이번 주 결정 (2026-10-18 사용자 확정)

사용자 요청("지금 미리 일주일동안의 개발동안 필요한 의사결정을 모두 결정해. 권한같은것도.")으로 한꺼번에 받았다. 모두 권장안이다.

| 항목 | 결정 | 뜻 |
|---|---|---|
| 개발 DB 컨테이너 | 켜도 됨 | 리드가 필요할 때 `flowmat-session1-db`를 `docker start`한다. 지우거나 초기화하지 않는다 |
| 커밋 전 마이그레이션 | 커밋 뒤에만 | V88–V94는 사용자가 커밋한 뒤 복제본 리허설을 거쳐 5434에 올린다 |
| 실제 API 확인 데이터 | 접두어로 만들고 지움 | 개발 DB에 고유 접두어로 만들고 끝나면 지운다. 로그인 제한과 `prj_demo_main`, BOM 삽입 금지는 그대로 지킨다 |
| 버리는 DB 컨테이너 | 허용 | 리허설용 `flowmat-*-check` 컨테이너를 리드가 만들고 지운다. 리드가 만든 것만 지운다 |
| 공유 상태 문서 | 정정·추가만 | `AGENT_HANDOFF.md` 같은 문서에서 사실이 바뀐 줄을 고치고 새 줄을 더한다. 남이 쓴 기록은 지우지 않는다 |
| 보고된 실패 | 기능 코드는 리드 | 리드가 만든 기능 코드의 결함은 리드가 고친다. 오류 담당의 테스트·CI 파일은 지시서로 넘긴다 |
| 문체 정리 | domain 문서 5개 | 금요일에 가장 딱딱한 domain 문서 5개만. 내용과 수용된 ADR 본문은 그대로 |
| 설비 날짜별 교대 | 날짜에만 묶어 둠 | ADR-014의 남은 항목. 작업자와 같이 판과 상관없이 그날 교대를 대신한다 |
| 금요일 기능 | 근무 시간에 맞춘 지연 | 연결 지연이 근무 밖에 끝나면 다음 근무 시작으로 미룬다 |
| 지연 달력 | 작업지시 설비 달력 | 생산 실행의 단계는 작업지시 설비의 가용 시간에 맞춘다. 설비나 달력이 없거나 생산에 연결되지 않은 실행은 지금처럼 미루지 않는다 |
| 외부 웹훅 규칙(나중) | 서명·재시도·소유자 | HMAC-SHA256 서명, 간격을 늘려 5번까지 재시도, 프로젝트 소유자만 등록, 보낼 내용은 DB에 먼저 적고(Outbox) 따로 보낸다 |
| 구현 중 새 설계 선택 | 권장안으로 진행 | ADR에 권장안과 "사용자 사전 위임(2026-10-18)"을 적고 구현한 뒤 보고한다. 데이터 삭제, 보안·권한 완화, 외부 공개, 기존 동작을 깨는 변경은 여전히 묻는다 |

바뀌지 않는 규칙: 브랜치·커밋·푸시는 하지 않는다. 적용된 마이그레이션은 주석까지 고치지 않는다. 다른 에이전트가 작업 중인 파일은 고치지 않는다. BOM 파일 없음, BOM 데이터 삽입 금지.

## 진행

- 10-17: 화요일과 수요일에 하려던 catalog 쪽 단계 B를 앞당겨 끝냈다. 서비스 18개, 29줄이다. 동결 목록은 48 → 19이고, catalog 밖에서 catalog repository를 쓰는 곳은 없다. 전체 백엔드 1,460건 통과(실패 0).
- 남은 19줄 중 project ↔ workflow 6줄과 project → user 1줄은 `ProjectAccessService`가 얽혀 있다. 단계 C를 정할 때 같이 본다.
- 10-18: 목요일 일을 앞당겼다. 지침 편집기의 공정 선택 e2e를 더했고, 생산 단계 시간 제한은 사용자 결정("늦음 표시만")대로 V92와 함께 구현했다. 전체 백엔드 1,484건 통과(실패 0, 오류 담당의 새 회귀 23건 포함), 프런트 Vitest 669건과 빌드 통과.
- 10-18: 수요일 일도 앞당겼다. quality → production 4줄과 quality → inventory 2줄을 공개 API로 바꿨다. 동결 목록 19 → 13. 전체 백엔드 1,484건 통과(실패 0).
- 10-18: 화요일 일도 했다. production → inventory 3줄과 production → bom 3줄을 바꿨다. bom은 Facts 인터페이스를 건드리지 않고 새 `BomStructureQuery`를 더했다. 동결 목록 13 → 7. 전체 백엔드 1,484건 통과(실패 0).
- 10-18: 남은 7줄은 사용자 요청("ADR 초안부터")대로 ADR-012 초안을, 다음 기능은 사용자 결정("근무표 이력")대로 ADR-013 초안을 썼다. 사용자가 둘 다 권장안대로 수용했다("Accept as recommended").
- 10-18: ADR-012대로 남은 7줄을 고쳤다. 동결 목록이 0줄이 되어 freeze를 풀고 저장소 파일을 지웠다. 실행 시작이 거는 워크플로 쓰기 락은 `WorkflowAccess.requireWriteAndLock`으로 옮겼다. 전체 백엔드 1,484건 통과(실패 0, 접근·보안 회귀 포함).
- 10-18: ADR-013대로 근무표 이력을 구현했다(2er, V93). 목요일과 금요일에 하려던 일이다. 전체 백엔드 1,485건 통과(실패 0), 프런트 Vitest 672건·빌드, 작업자 모의 e2e 10개 통과.
- 10-18: 다음 기능은 사용자 결정("설비 달력 이력")대로 ADR-014 초안을 썼다. 사용자가 권장안대로 수용했다("Accept as recommended").
- 10-18: ADR-014대로 설비 달력 이력을 구현했다(2es, V94). 목요일 일이다. 전체 백엔드 1,509건(254클래스) 통과(실패 0), 프런트 Vitest 675건·typecheck·빌드, 모의 e2e 185건 통과(실패·flaky 0, 실제 API용 38건 조건부 제외).
- 10-18: 금요일 기능을 당겨 ADR-015(근무 시간에 맞춘 연결 지연)를 썼다. 핵심은 사용자 결정, 세부는 사용자 사전 위임(2026-10-18)대로 권장안이다.
- 10-18: ADR-015대로 근무 시간에 맞춘 연결 지연을 구현했다(2et, 마이그레이션 없음). 초안의 결정 6("`schedule`로 앞당김")은 생산 단계에 그 API가 없어, "지연이 끝났고 지금 설비가 일하면 시작"으로 구현 전에 고쳤다. 전체 백엔드 1,511건(255클래스) 통과(실패 0), 프런트 Vitest 676건·typecheck·빌드, 모의 e2e 185건 통과(실패·flaky 0, 실제 API용 38건 조건부 제외).
- 10-18: 문체 정리(사용자 결정 "domain 문서 5개")를 당겨 했다. 딱딱한 문체 점수(존댓말 끝맺음, 괄호·화살표·굵은 글씨 밀도, 문장 길이)가 높은 domain 문서 5개(`work-order-readiness`, `stock-ledger`, `quality-inspection`, `stock-alert`, `inventory-bom-lot-contract`)를 짧고 평범한 "~다" 문장으로 고쳤다. 제목·표·코드·링크·숫자·규칙 번호는 그대로임을 검사 스크립트로 확인했다. 계약서의 [구현 결정]·[확정] 항목, D2 검토 현황, §8 현황표는 결정 기록이라 한 글자도 바꾸지 않았다.

## 남은 7줄

남은 7줄은 설계나 담당 구역이 걸려 있어 사용자 결정을 기다린다.

| 줄 | 무엇을 하나 | 걸리는 것 |
|---|---|---|
| `ProjectAccessService` → workflow repository 4줄 | 워크플로, 공정, 포트, 연결 id로 프로젝트를 찾아 접근을 검사하고, 워크플로 엔티티를 돌려준다 | 여러 모듈이 부르는 접근 검사의 핵심이다. project ↔ workflow 순환을 어떻게 끊을지 정해야 한다 |
| `WorkflowServiceImpl`, `WorkflowTemplateServiceImpl` → `ProjectRepository` 2줄 | 첫 워크플로를 만들거나 지울 때 프로젝트의 현재 워크플로(`current_workflow_id`)를 저장한다 | 읽기가 아니라 쓰기라 project 쪽 명령 API가 필요하다 |
| `ProjectInviteServiceImpl` → `UserRepository` 1줄 | 초대 메일 주소로 사용자를 찾고, 초대한 사람 이름을 읽는다 | user 모듈은 인증 쪽이다 |

결정은 [ADR-012](../architecture/adr/ADR-012-workflow-access-boundary.md)에서 했고, 10-18에 결정대로 모두 고쳤다(2eq).

## 하지 않는 것

- 브랜치, 커밋, 푸시. 사용자가 한다.
- 적용된 마이그레이션(V1–V87) 수정.
- 다른 에이전트가 고치는 중인 파일 수정. 고쳐야 하면 먼저 묻는다.
- 멈춘 개발 DB 컨테이너를 묻지 않고 켜기.

## 위험

- 커밋이 늦어지면 개발 DB 적용이 밀린다. 그동안 실제 API 확인은 V87 기준으로만 된다.
- 단계 B는 여러 서비스를 건드린다. 하루 단위로 끊고, 날마다 전체 회귀를 한 번 돌린다.
- 커밋 전 마이그레이션이 V88–V94 일곱으로 늘었다. 한 번에 리허설한다. V93·V94는 기존 교대를 판으로 옮기므로 행 수를 꼭 비교한다.
