# 주간 개발 계획 (2026-10-19 ~ 10-23)

작성: 2026-10-17, 리드. 기준은 그날 작업 트리와 [WORKBOARD](WORKBOARD.md)다. 일이 끝나거나 바뀌면 여기 표시하고, 끝난 일은 WORKBOARD §2에도 적는다.

## 시작 상태

- 2eh–2el(Split, 손실률, 지연, 설비 동시 작업 수, 생산 실행의 공정 단계)은 로컬 검증까지 끝났다. 전체 백엔드 1,460건이 통과했다.
- 커밋 전 마이그레이션이 넷이다. V88(Join), V89(Split), V90(설비 동시 작업 수), V91(지침 단계의 공정). 개발 DB 5434는 V87이다.
- 개발 DB 컨테이너 `flowmat-session1-db`가 10-17 낮부터 멈춰 있다(Exited 0). 누가 멈췄는지는 모른다.
- 모듈 경계 단계 B는 105곳 중 48곳이 남았다. inventory → catalog 14곳, production → catalog 7곳, quality → catalog 5곳이 크다.
- 문서 문체 정리는 `domain/equipment.md` 한 파일만 했다.

바뀌지 않는 규칙: 브랜치·커밋·푸시는 하지 않는다. 적용된 마이그레이션은 주석까지 고치지 않는다. 다른 에이전트가 작업 중인 파일은 고치지 않는다. BOM 파일 없음, BOM 데이터 삽입 금지.

- 10-19: 오류 담당이 넘긴 세 가지를 반영했다. snapshot의 큰 지수 거절과 단계 API 본문 오류 400(Flow Run F17), 생산 단계 완료의 정확한 소수, 작업자 시간 화면의 입력 보존(작업자 달력 LB12). 오류 담당의 테스트 4개를 그대로 넣었다.
- 10-19: 작업자 시간이 생산 단계를 고를 수 있게 했다(2ez, V98, ADR-021). 고른 단계의 실제 시간 × 몫이 분의 시작값이다.
- 10-19: 연결 지연을 근무 시간으로만 셀 수 있게 했다(2fa, V99, ADR-022, ADR-015 "결정하지 않은 것"). 기본은 지금처럼 모든 시간이다.
- 10-19: 단계 작업자 시간의 후속 둘을 붙였다(2fb, V100, ADR-023). 보정 줄도 단계를 고르고, 작업지시 대비에 공정별 실제 분이 보인다.
- 10-19: 판의 저장 이력을 남기게 했다(2fc, V101, ADR-024, ADR-017 "결정하지 않은 것"). 근무표 판과 설비 달력 판을 저장·지울 때마다 그때의 교대와 사유가 남고, Workers와 설비 일정에서 본다.
- 10-19: 작업지시 준비 점검이, 실행이 공정 단계 없이 시작될 때(발행 revision이 그래프로 돌 수 없음) 미리 경고한다(2fd, 마이그레이션 없음). 벤치마크의 실행 전 검증(preflight) 가운데 빠져 있던 한 줄이다.
- 10-19: 오류 담당이 넘긴 설비 시간·setup 화면의 입력 보존을 반영했다(작업자 시간 화면과 같은 방식).
- 10-19: 사용자 계획 1–7을 마쳤다. 사용자가 V95–V101과 2ex–2fd를 커밋했다(`86949f0`, 최신 main `2cd8280` 위). 5434를 백업하고 V88–V94를 적용해 smoke를 했다(지문은 Flyway 줄만 다름, 확인 6줄 ok, 주요 GET 28개 200). 통합 snapshot을 다시 검증했다. 전체 백엔드 1,762건(278클래스) 실패 0이다. 프런트는 잠금 파일대로 설치한 격리 복사본에서 Vitest 691건·typecheck·lint·빌드가 통과했고, 모의 e2e는 204 통과·40 건너뜀·1 실패다. 실패 1건은 부하가 클 때의 스캐너 경합이라 오류 담당에게 넘겼다(단독 3회는 통과). 이어 V95–V101 복제본 리허설(확인 10줄 ok, 행 수 그대로, GET 28개와 새 API 6개 200)을 거쳐 5434에 적용했다. 5434는 V101이다.
- 10-19: 계획 8. 단계 C(ADR-018)를 Accepted로 했다. 다른 도메인 엔티티 의존 기준선은 39줄(21클래스, import 37곳과 import 없는 2줄)이다. `ModuleBoundaryTest`에 동결 규칙을 더해 새 의존은 실패한다. 치환은 하지 않았다.
- 10-19: 오류 담당이 넘긴 이력 화면 수정(이력 조회가 403으로 거절되면 앞서 받은 줄을 숨김)과 그 e2e를 반영했다.
- 10-23: 오류 담당이 넘긴 이력 서버 수정 둘(이력에 DB에 저장된 교대 시각, 팀 근무표 복사 교착)을 반영했다. 관련 155건 통과.
- 10-23: 계획 9. ADR-024를 날짜별 교대·쉬는 날·설비 정지로 넓혔다(2fe, V102 커밋 전). 저장·지움·복사마다 그때의 것이 남고, Workers와 설비 일정의 새 이력에서 본다.
- 10-23: 계획 10. 작업자 인건비 결정을 ADR-025로 적었다(소유자만 보는 금액, 프로젝트 × 작업자 단가, 적용 시작일 이력). 구현은 2ff로 남았다.
- 10-23: 이어서 ADR-025를 구현했다(2ff, V103 커밋 전). 소유자만 단가를 정하고 실행·작업지시 인건비를 본다.
- 10-23: 이력 목록이 최신 100줄 뒤도 볼 수 있게 했다(2fg, 마이그레이션 없음). 10-20에 만든 판 이력 검색 API를 화면에 잇고, 날짜 이력에도 같은 검색을 더했다.
- 10-23: ADR-025의 남은 둘을 권장안으로 정했다(사용자 "ㄱ"). 인건비는 원가 합계에 넣지 않고, 작업자의 첫 단가만 처음부터 적용할 수 있다(2fh). 출퇴근 대조는 ADR-026 초안만 썼다(사용자 결정 대기).
- 10-23: 설비 부하표에서 작업지시를 새 시작으로 옮길 수 있게 했다(2fi, 화면만). 초안은 지금 저장, 승인 작업지시는 소유자의 사유 있는 일정 변경을 쓴다.
- 10-24: 출퇴근 기록을 더했다(2fj, V104 커밋 전). 사용자가 결정을 권장안으로 맡겨 ADR-026을 Accepted로 올렸다. 본인과 소유자만 출근·퇴근을 적고 보며, 날마다 실행 작업자 시간과 견준다.
- 10-24: 실행 투입을 취소할 때 돌아온 재고를 작업지시에 다시 할당할 수 있게 했다(2fk, 마이그레이션 없음, 재고 할당 R4). 묻지 않으면 예전처럼 자유 재고다.
- 10-24: 보관 위치에 보관 조건을 더했다(2fl, V105 커밋 전). 안쪽 위치가 물려받고, 품목 조건과 다른 재고 행과 등록·이동을 알린다. 막지는 않는다.
- 10-24: 구매 발주를 더했다(2fm, V106 커밋 전, ADR-027 Accepted). 새 `purchasing` 컨텍스트에서 초안 → 주문 → 줄마다 입고하고, 받은 재고는 원장에 발주 참조로 남는다. 자재 소요 예정 공급 연결은 다음(2fn).
- 10-24: 주문한 발주의 남은 양을 자재 소요의 공급으로 세고, 재주문 목록에서 나머지를 초안 발주서로 만들 수 있게 했다(2fn, 마이그레이션 없음).
- 10-24: 발주를 뒤따르기 쉽게 했다(2fo, 화면만). 예정일이 지난 주문 발주를 표시하고, 발주로 받은 LOT의 입고 검사를 바로 열며, 쓴 공급처를 제안한다.
- 10-24: 열린 작업지시가 부족하게 남기는 사 오는 자재를 초안 발주서 하나로 만들 수 있게 했다(2fp, 화면만). 같은 날 발주 입고의 받은 시각 정밀도 결함을 고쳤다(2fm 보완).
- 10-24: LOT 상세가 들여온 발주와 공급처를 보여 주고, 공급처 반품 부적합이 그 공급처를 짚는다(2fq, 화면만).
- 10-24: 발주 줄에 단가를 적고 줄·발주 금액을 보게 했다(2fr, V108 커밋 전, ADR-027 결정 9). 품목 단가는 저절로 바뀌지 않고, 받은 단가를 확인 뒤 손으로 품목 단가로 쓸 수 있다(2fs, 화면만).
- 10-24: 발주서를 새 창에서 인쇄할 수 있게 했다(2ft, 화면만). 이메일·PDF로 보내기는 아직 정하지 않았다.
- 10-24: 작업지시 필요 CSV 끝에 주문 중(`on_order`) 열을 더했다(2fu, 화면만).
- 10-24: 공급처 목록을 만들었다(2fv, V109 커밋 전, ADR-027 결정 10). 목록이 있으면 발주서는 활성 공급처만 쓰고, 납기가 예정일을 제안한다.
- 10-24: 주문한 발주서의 예정일을 사유와 함께 옮기고 이력을 남기게 했다(2fw, V110 커밋 전, ADR-027 결정 11).
- 10-24: 공급처마다 첫 예정일과 지금 예정일을 지켰는지 보이게 했다(2fx, 화면만).
- 10-24: 열린 작업지시의 자재가 언제 처음 모자라는지(발주가 늦게 오는 경우 포함) 보이게 했다(2fy, 화면만).
- 10-24: 받은 발주 재고를 공급처로 돌려보내게 했다(2fz, V111 커밋 전, ADR-027 결정 12). 격리된 재고도 돌려보낼 수 있고 받은 양은 그대로다.
- 10-24: 품목마다 평소 공급처를 두고, 재주문·작업지시 부족분 초안이 공급처마다 나뉘게 했다(2ga, V112 커밋 전, ADR-027 결정 13).
- 10-24: 소유자가 정한 한도 이상인 발주서는 소유자 승인 뒤에만 주문되게 했다(2gc, V113 커밋 전, ADR-027 결정 14). 인쇄용 발주서에는 공급처 코드가 나온다(2gb).
- 10-24: 승인이 필요한 발주 초안은 소유자에게, 승인은 초안을 저장한 사람에게 앱 안 알림으로 간다(2gd, 마이그레이션 없음).
- 10-24: 실사 계획을 구성원에게 맡기고 알리게 했다(2ge, V114 커밋 전). 블라인드 기준 수량은 여전히 소유자만 본다.
- 10-24: 평소 공급처에 그 공급처의 단가를 두고 공급처별 초안이 그 단가로 시작하게 했다(2gg, V115 커밋 전). NCR에서 반품할 발주로 바로 간다(2gf).
- 10-24: 발주서에 도착 장소를 두고, 위치별 재주문 목록이 그 장소로 오는 주문만 세게 했다(2gh, V116 커밋 전, ADR-027 결정 15).
- 10-24: 공급처별 지출 표(2gj)를 더하고, 프로젝트가 고르면 보관 조건이 다른 위치로 재고가 들어오는 것을 막게 했다(2gk, V117 커밋 전).
- 10-24–25: 단계 C(ADR-018) 줄여 가기를 시작했다(사용자 지시, 시작점은 리드). 2gl(접근 검사·품목 삭제 검사), 2gm(inventory → catalog), 2gn(production → catalog), 2go(production → bom), 2gp(production → inventory)로 동결 목록이 39줄에서 5줄이 됐고, 2gr(production → workflow)로 0줄이 되어 동결을 풀었다(2gs). 이제 다른 도메인 엔티티를 쓰면 바로 실패한다. 동작은 바꾸지 않았고, 흐름 규칙은 품목의 모든 속성을 예전처럼 읽는다(결정 5). Docker 엔진이 멈췄다가 사용자가 다시 시작한 뒤 전체 회귀(백엔드 2,141건)가 통과했다. Facts(json) API를 모두 지웠다(`BomPlanningQuery`, `CatalogItemFactsQuery`, `StockFactsQuery`, `WorkflowProductionQuery`의 작업흐름·공정·포트 조회; 2gp·2gq·2gt). 실행 기록이 게시 개정 스냅숏 JSON을 직접 읽던 일도 workflow로 옮겼다(2gu).
- 10-25: 반품이 그 재고를 돌려보내기로 한 NCR을 적고, NCR이 그 반품을 보게 했다(2gv, V118 커밋 전, ADR-027 결정 16).
- 10-25: 공급처 납기 표를 기간으로 거르고, 줄 단위로 제때 왔는지와 늦게 온 발주의 평균 늦은 날을 보이게 했다(2gw, 화면만).
- 10-25: 주문할 때 공급처가 부르는 품목 코드를 발주서 줄에 남겨, 나중에 바꿔도 주문한 발주서는 그대로 인쇄되게 했다(2gx, V119 커밋 전, ADR-027 결정 17).
- 10-25: 반품할 때 교체품을 같은 발주서로 받을지 고르게 해, 교체를 기다리는 양이 주문 중으로 돌아가고 다 받은 발주서도 다시 받는 중이 되게 했다(2gy, V120 커밋 전, ADR-027 결정 18).
- 10-25: 교체 없이 돌려보낸 것을 공급처가 갚을 대변으로 보이고, 반품마다 공급처가 갚은 금액과 대변표 번호를 남기게 했다(2gz, V121 커밋 전, ADR-027 결정 19).
- 10-25: 품목마다 공급처별 마지막·최저 단가와 단가 이력을 주문한 발주서에서 견주어 보게 했다(2ha, 화면만, ADR-027 결정 20).
- 10-25: 소유자가 금액대별로 편집자 승인 단계를 두고, 초안이 필요한 승인을 낮은 금액부터 차례로 받게 했다(2hb, V122 커밋 전, ADR-027 결정 21).
- 10-25: 남긴 공급처 대변을 사유와 함께 고치거나 취소하고, 고친 것을 모두 남기게 했다(2hc, V123 커밋 전, ADR-027 결정 22).
- 10-25: 작업자의 출퇴근을 고른 기간(62일까지)으로 CSV로 받게 했다(2hd, 화면만, ADR-026 결정 13).
- 10-25: 작업지시에 공정마다 계획 작업자 분을 두고, 실행에서 공정마다 든 분 옆에 보이게 했다(2he, V124 커밋 전, ADR-023 결정 5–7).
- 10-25: 계획 기간 제안이 공정 계획의 노동 시간을 세고, 설비 없는 작업지시도 인력의 근무 시간으로 날짜를 제안하게 했다(2hf, 마이그레이션 없음, ADR-023 결정 8).
- 10-30: 계획 제안의 노동을 그 시각에 일하는 사람의 몫만큼 쌓고, 몫 100% 미만인 사람만 있는 설비 없는 작업지시도 날짜를 받게 했다(2hg, 마이그레이션 없음, ADR-023 결정 9–10).
- 10-30: 소유자가 연장·야간·휴일 할증을 시작일이 있는 이력으로 두고, 작업자 출퇴근을 근무일마다 할증을 더한 지급으로 보게 했다(2hh, V126 커밋 전, ADR-028).
- 10-30: 실행·작업지시 인건비에도 그날 지급 비율로 할증 포함 금액을 냈다(2hi, 마이그레이션 없음, ADR-028 결정 10–12).
- 10-30: 할증 규칙에 주 단위 연장(주 기준 시간·가산·시작 요일)을 더했다(2hj, V127 커밋 전, ADR-028 결정 13–15).
- 10-30: 할증 규칙이 정하면 작업자의 쉬는 날 근무에도 휴일 가산을 붙였다(2hk, V128 커밋 전, ADR-028 결정 16–17).
- 10-30: 할증 규칙에 휴일 연장(휴일 기준 시간을 넘는 분의 더 높은 가산)을 더했다(2hl, V129 커밋 전, ADR-028 결정 18–19).
- 10-30: 작업자마다 자신의 할증 규칙을 두어 프로젝트 규칙을 대신하고, 다시 프로젝트 규칙을 따르게도 했다(2hm, V130 커밋 전, ADR-028 결정 20–22).
- 10-31: 공정 계획의 공정 분을 사람별로 나누고, 작업지시 대비에 공정마다 각 사람의 몫과 기록한 분을 보였다(2hn, V131 커밋 전, ADR-023 결정 11–13).
- 10-31: 실행 작업자 시간에 시작·끝 시각을 둘 수 있게 하고, 할증 포함 인건비가 그 시각의 연장·야간 할증을 따르게 했다(2ho, V132 커밋 전, ADR-028 결정 23–26).
- 10-31: 출퇴근 대비도 시각 있는 작업자 시간을 시작한 날로 세게 했다(2hp, 마이그레이션 없음, ADR-028 결정 27).
- 10-31: 계획 제안의 노동 시간이 사람별로 나눈 공정 몫을 따르게 했다(2hq, 마이그레이션 없음, ADR-023 결정 14–16).
- 10-31: 나눈 공정이 있는 계획 제안이 워크플로의 공정 순서를 따르게 했다(2hr, 마이그레이션 없음, ADR-023 결정 17–19).
- 10-31: 계획 제안에 누가 어느 공정을 언제 하는지 보이게 했다(2hs, 마이그레이션 없음, ADR-023 결정 20–21).
- 10-31: 여러 작업지시 계획에도 사람별 일정을 보이게 했다(2ht, 프런트만).
- 10-31: 출퇴근 대비가 보정으로 더한 시간을 실행의 원래 끝 날로 세게 했다(2hu, 마이그레이션 없음, ADR-028 결정 28).

## 남은 7줄

남은 7줄은 설계나 담당 구역이 걸려 있어 사용자 결정을 기다린다.

| 줄 | 무엇을 하나 | 걸리는 것 |
|---|---|---|
| `ProjectAccessService` → workflow repository 4줄 | 워크플로, 공정, 포트, 연결 id로 프로젝트를 찾아 접근을 검사하고, 워크플로 엔티티를 돌려준다 | 여러 모듈이 부르는 접근 검사의 핵심이다. project ↔ workflow 순환을 어떻게 끊을지 정해야 한다 |
| `WorkflowServiceImpl`, `WorkflowTemplateServiceImpl` → `ProjectRepository` 2줄 | 첫 워크플로를 만들거나 지울 때 프로젝트의 현재 워크플로(`current_workflow_id`)를 저장한다 | 읽기가 아니라 쓰기라 project 쪽 명령 API가 필요하다 |
| `ProjectInviteServiceImpl` → `UserRepository` 1줄 | 초대 메일 주소로 사용자를 찾고, 초대한 사람 이름을 읽는다 | user 모듈은 인증 쪽이다 |

결정은 [ADR-012](../architecture/adr/ADR-012-workflow-access-boundary.md)에서 했고, 10-18에 결정대로 모두 고쳤다(2eq).

## 하지 않는 것

- 브랜치, 커밋, 푸시. 사용자가 한다.
- 적용된 마이그레이션(V1–V87) 수정.
- 다른 에이전트가 고치는 중인 파일 수정. 고쳐야 하면 먼저 묻는다.
- 멈춘 개발 DB 컨테이너를 묻지 않고 켜기.

## 위험

- 커밋이 늦어지면 개발 DB 적용이 밀린다. 그동안 실제 API 확인은 V87 기준으로만 된다.
- 단계 B는 여러 서비스를 건드린다. 하루 단위로 끊고, 날마다 전체 회귀를 한 번 돌린다.
- 커밋 전 마이그레이션이 V88–V95 여덟으로 늘었다. 한 번에 리허설한다. V93·V94는 기존 교대를 판으로 옮기므로 행 수를 꼭 비교한다.
