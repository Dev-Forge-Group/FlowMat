# 월간 개발 계획 (2026-12-21 ~ 2027-01-15): 돌려 보기에 시간을, 그리기 층에 동시 편집을

작성: 2026-11-21. 사용자 지시(11-21): "flowmat 작업 계속 이어가. 다음달 계획도." 범위는 [지난 계획](MONTH-PLAN-2026-11-23.md)의 "다음 달 후보"(4주차 3번)를 그대로 따른다. 세부는 2026-10-24 위임에 따라 권장안이다. 일이 끝나거나 바뀌면 여기 표시하고, 끝난 일은 [WORKBOARD](WORKBOARD.md)에도 적는다.

## FlowMat의 본질

**흐름을 설계하고, 설계한 대로 돌려 보고, 실제로 돌린 것을 맞게 남긴다.** 지난달에 편집기가 흐름을 그리는 즉시 검사하고 양과 경로를 따라가게 됐다. 이번 달에는 두 가지를 더한다.

- **언제.** 실제 실행에서 단계는 연결 지연과 설비·인력의 근무 시간에 따라 기다린다. 돌려 보기도 같은 이유로 같은 만큼 기다려야 한다.
- **함께 그리기.** 흐름은 여럿이 함께 그린다. 그리기 층(도형·선·글)은 지금 문서 전체를 저장하므로 두 사람의 편집 중 하나가 사라질 수 있다.

## 지금 상태 (2026-11-21, PR #130 기준)

- **흐름 커널**(`compute/flow-kernel`, ADR-040).
  - 검증·경로 계산·실행 따라가기가 Java가 적은 답과 모두 같다. 검증 170, 경로 130, 실행 94, 조건식 1,641이다.
  - 편집기 모듈은 611KB(gzip 179KB)다.
  - 서버는 Java를 둔다. Chicory로 돌린 커널은 Java보다 18배 느렸다.
- **시간 계산은 Java에만 있다.**
  - 설비 가용 시간: `EquipmentScheduleService.window`. 달력 판, 휴일, 날짜별 교대, 정지, 프로젝트 시간대를 반영한다.
  - 함께 일하는 구간: `ProductionRunWorkingTime`. 설비 가용 시간과 몫이 100%인 인력의 근무를 겹친다.
  - 단계 예정 시각:
    - 지연이 끝난 뒤 함께 일하는 구간이 시작할 때로 미룬다(ADR-015·016).
    - 근무 시간으로 세는 지연은 그 구간을 지연만큼 쌓는다(ADR-022).
  - 읽기 API는 설비의 `/availability`뿐이다. 작업지시의 함께 일하는 구간을 내는 곳은 없다.
- **협업.**
  - 공정·포트·연결은 항목마다 REST로 바꾼다. 서버가 번호(`seq`)를 붙인 그래프 변경을 STOMP로 보내고, 브라우저가 차례로 적용한다. 번호가 비면 다시 받는다.
  - 커서, 편집 중 표시, 자유 그리기 미리보기는 presence로 보낸다.
  - 그리기 층(편집기 문서)은 문서 전체를 저장한다. 다른 사람이 먼저 저장했으면 409를 받고 서버 판을 다시 보여 준다.
- **화면.** 큰 화면 셋이 모두 800줄 이하다. 그리기 층의 문서 계산은 `model/workspaceEditorDocument.ts`에 있다. 요소 단위 변경을 붙일 자리가 생겼다.
- **CI**: 백엔드 약 8분, 모의 E2E 3조각 약 7분, 실 API E2E 약 7분.

## 진행

- **1주차 1번 ADR-041: 끝(Accepted).** [ADR-041](../architecture/adr/ADR-041-try-it-time.md). 결정 4는 그래프 실행이 시스템 시계를 쓴다는 것을 보고 고쳤다. 고정 입력의 답은 서버에서 실제로 돌린 시각이 아니라, 라우터와 같은 순수 함수가 낸다.
- **4주차 1·2번 ADR-042와 서버: 끝(2026-11-22, 일찍).** [ADR-042](../architecture/adr/ADR-042-drawing-layer-element-changes.md).
  - `PATCH /workflows/{id}/editor-document/elements`가 요소의 추가·바꾸기·지우기를 받는다. 바꾸기와 지우기는 편집을 시작한 요소의 판(`baseVersion`)을 보낸다.
  - 한 요청은 다 되거나 하나도 안 된다. 충돌이 있으면 409이고, 충돌한 요소를 이름으로 말한다.
  - 마이그레이션은 없다. 요소의 판은 V12부터 있다.
  - `EditorElementChangesIntegrationTest` 4개를 붙였다. 다른 요소는 둘 다 남는다. 옛 판으로 바꾸면 아무것도 안 바뀐다. 이미 있는 id 추가, 옛 판 지우기, 지워진 요소 바꾸기, 요청 오류, 보기 권한 403도 본다. 바깥 사용자 403은 `ProjectAccessIntegrationTest`에 더했다.
  - 남은 것: 4주차 3번 편집기(요소 판을 어댑터에 두고, 바뀐 요소만 보내기)와 두 브라우저 실 API 테스트.

  - 패널에 작업지시(이 흐름의 취소·완료되지 않은 것)와 시작 시각을 고르는 칸이 생겼다. 고르지 않으면 지금처럼 양만 따라간다.
  - 고르면 구간 API를 시작 시각부터 7일 묻고, 커널로 따라간다.
  - 단계마다 시작할 수 있는 때와 기다린 것을 생산 단계 화면과 같은 말로 보인다(`from 2026-12-21 13:00 (waits for PRESS, kim)`). 설비는 코드로 부른다(API의 `equipmentCode`).
  - 전체가 언제 끝나고 얼마나 걸리는지도 보인다.
  - 순수 함수(`startTime`, `kernelTime`, `timeNotes`, `timeSummary`, `duration`)에 단위 테스트를 붙였다.
  - 모의 브라우저 테스트(`try-flow.spec.ts`)가 근무 시간 지연과 점심시간 기다림을 본다.
- **3주차 2번 같은 답 확인: 끝(2026-11-21, 일찍).** `try-flow-real-api.spec.ts`의 두 번째 테스트:

  - 편집기의 "Try it"에서 같은 작업지시를 고르면 같은 시각과 설비 코드가 나온다.

- **2주차 2번 구간 읽기 API: 끝(2026-11-21, 일찍).** `GET /work-orders/{id}/working-time`([worker-calendar](../domain/worker-calendar.md) WC68). `ProductionRunWorkingTime`과 같은 계산이다. `TryItTimeIntegrationTest` 4개:

  - 설비도 인력도 없는 작업지시는 모든 시간이다.
  - 기간 오류도 본다.

  - `walk` 요청에 `time`을 주면 답에 `times`가 붙는다.
  - `time.json` 67개가 Rust, WASM(`check-fixtures`), TypeScript(`flowKernel.test.ts`)에서 모두 Java와 같다. 모듈은 611KB에서 635KB(+3.9%, gzip 189KB)가 됐다.
- **1주차 3번 고정 입력: 끝(2026-11-21, 일찍).**
  - 라우터의 시각 규칙을 순수 함수 `FlowRunTiming`으로 뗐다(지연, 근무 시간 지연, 합류, 근무 밖 기다림, 마이크로초). 라우터와 `FlowRunStepAvailability`가 이것을 부르므로, 돌려 보기와 서버가 같은 규칙을 쓴다. `WorkingStretches`는 `flowrun`의 공개 계약으로 옮겼다(ADR-041 결정 3). 단위 테스트 9개를 붙였고, 백엔드 전체 3,376개가 통과한다.
  - `time.json`(`FlowKernelTimeFixtureTest`, 서버를 띄우지 않는 단위 테스트): 지연이 있는 흐름 67개.
    - 단계와 합류의 도착은 `walk.json`(서버가 지연을 뺀 판으로 돌린 것)에서 가져온다. 지연은 `routing.json`의 원래 그래프에서 가져온다.
    - 시작 시각, 함께 일하는 구간, 설비·인력은 시드로 만든다.
    - 걸리는 것: 지연 34, 근무 시간 지연 8, 그 대신 모든 시간 1, 근무 밖 기다림 7, 지연이 있는 합류 5, 게이트웨이가 넘긴 시각 10, 구간 없음 7, 오프셋이 바뀌는 구간 15, 소수 초 시작 17.
    - 시각은 `ISO_OFFSET_DATE_TIME`으로 쓴다(초는 늘 쓰고, 소수는 필요한 자리만).
- **1주차 2번 Java 구간 계산의 순수 함수: 끝(2026-11-21, 일찍).** `WorkingStretches`(`firstStart`, `afterWorking`, `intersect`)를 `ProductionRunWorkingTime`에서 뗐다. 단위 테스트 9개를 붙였다. 근무 시간·지연·합류 테스트 9클래스 94개(통합 8클래스, `FlowRunStepAvailabilityTest`)가 그대로 통과한다.

## 한 달 뒤 목표

1. **시간을 넣은 돌려 보기.** "Try it"에서 작업지시를 고르면 단계마다 시작할 수 있는 시각과 기다리는 이유(지연, 설비, 인력)가 보인다.
   - 같은 작업지시로 서버에서 돌린 생산 실행의 예정 시각(`scheduledAt`)과 초 단위까지 같다.
   - 커널은 달력을 계산하지 않는다. Java가 계산한 함께 일하는 구간을 입력으로 받는다.
2. **그리기 층의 동시 편집.** 두 사람이 서로 다른 요소를 동시에 고쳐도 둘 다 남는다.
   - 같은 요소의 같은 필드를 고치면 나중에 쓴 쪽이 이기고, 진 쪽에 보인다.
   - 그래프(공정·포트·연결)는 지금 방식을 둔다. 서버 검사와 발행이 그 경로에 있기 때문이다.
3. **릴리스 후보.** `v0.9.0-rc.1`(NVD 키가 들어오면)과 그 뒤 PR #130을 넣은 `v0.9.0-rc.2`. 점검표를 같은 커밋에서 다 통과한다.

## 원칙

- **같은 답이 먼저다.** 지난달처럼 Java가 고정 입력에 답을 적고, 커널은 그 답을 다 맞춘 뒤에만 쓴다.
- **정본은 하나다.** 달력·시간대·휴일은 Java 하나에서 계산한다. 커널에는 구간 계산 결과만 들어간다. 같은 규칙을 두 언어로 쓰지 않는다.
- **원장과 실행은 건드리지 않는다.** 돌려 보기는 DB에 쓰지 않는다. 생산 실행의 시간 규칙을 바꾸면 Java의 답을 다시 쓰고 diff를 읽는다.
- **숫자로 정한다.** 동시 편집 방식(요소 단위 변경과 CRDT 라이브러리)은 크기와 충돌 사례를 재고 정한다.

| 1 | ADR-042 그리기 층의 변경 | 정하는 것: 요소 단위 변경(추가·필드 바꾸기·삭제·순서)의 모양, 요소별 판(`version`), 같은 필드는 나중 쓴 쪽, 서버가 번호를 붙여 보내는 방식(그래프 변경과 같은 `seq`), 문서 전체 저장을 언제까지 받을지. CRDT 라이브러리(Yjs 등)를 쓸지는 크기와 사례로 비교해 적는다 |
| 2 | 서버 | `PATCH /workflows/{id}/editor-document/elements`(변경 여럿, 원자적). 요소의 판이 다르면 그 요소만 409다. 다른 요소는 적용한다. 통합 테스트가 두 사용자의 다른 요소 변경이 둘 다 남는지 본다. 마이그레이션이 필요하면 새 번호로 더한다 |
| 3 | 편집기 | `workspaceEditorDocument`의 계산 결과를 요소 변경으로 바꿔 보낸다. 다른 사람의 변경이 오면 끌고 있는 요소만 빼고 적용한다. 실 API 브라우저 테스트: 두 브라우저가 다른 도형을 동시에 옮기면 둘 다 남는다 |

## 위험

- **시각이 초 단위로 어긋남.** 서버는 `OffsetDateTime`과 `Duration`, 커널은 오프셋 붙은 문자열을 쓴다. 나노초 반올림이나 오프셋 표기 차이로 어긋날 수 있다. 고정 입력에 소수 초와 오프셋이 바뀌는 사례를 넣는다.
- **구간이 큼.** 366일까지 찾으면 구간이 수백 개다. API는 기간을 받고 기본은 7일로 한다. 모자라면 편집기가 다음 기간을 다시 묻는다(서버가 7·31·366일로 넓혀 가는 것과 같다).
- **동시 편집의 범위.** 문서 전체 저장을 쓰는 곳(주석 어댑터, 실행 취소 이력)이 많다. 4주차는 이동·스타일·삭제부터 하고, 그룹·순서는 다음으로 넘길 수 있다.
