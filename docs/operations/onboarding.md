# 공장별 도입 시간

> **현행 문서** · 확인 2026-11-23(`main` V140). 질의나 기준을 바꾸면 같은 변경에서 고친다.

[로드맵](../status/ROADMAP-2026-11-23.md) §5의 2번은 파일럿부터 공장마다 도입 비용을 재라고 한다. 이 수치는 판정 1(2027-02-19)과 판정 2(2027-05-21)에서 가격 가설과 비교한다. 잴 것은 넷이다.

- 시작 준비 시간
- 자료 옮기기 시간(품목·BOM·재고)
- 교육 시간
- 우리 쪽의 공장당 월 운영비

앞의 둘은 DB에 이미 있는 기록으로 잰다(§1). 뒤의 둘은 DB에 없으므로 사람이 적는다(§2). 새 추적 코드는 넣지 않았다.

## 1. DB로 재는 것

```bash
docker exec -i <DB 컨테이너> psql -U <사용자> -d <DB> -v days=120 -f - < scripts/ops/onboarding.sql
```

`days`는 최근 며칠 안에 만든 프로젝트를 볼지 정하고, 기본값은 120일이다. 질의는 읽기만 한다. 임시 뷰를 만들므로 원본 DB에서 돌린다([주간 사용량](usage-weekly.md)과 같다). 결과에는 프로젝트 ID와 숫자만 있다. 사용자, 이름, 수량은 나오지 않는다.

**첫 표: 프로젝트를 만든 때부터 각 단계를 처음 한 때까지의 시간(시간 단위)**

비어 있으면 아직 그 단계를 하지 않은 것이다.

| 칸 | 처음 한 일 |
|---|---|
| `h_item` | 품목을 만들었다 |
| `h_bom` | BOM을 승인했다 |
| `h_stock` | 재고 원장에 줄을 썼다(입고 등) |
| `h_published` | 흐름을 게시했다 |
| `h_plan` | 계획을 확정했다(ADR-043) |
| `h_run` | 생산 실행을 끝냈다 |
| `h_data_in` | 자료 옮기기: 첫 품목부터 첫 BOM·첫 재고·첫 게시 중 가장 늦은 것까지 |
| `items_28d` | 첫 28일 동안 만든 품목 수 |
| `sample_like` | 게시가 만든 지 5분 안에 있었다. "견본으로 시작"이나 스크립트로 만든 프로젝트이니 공장의 도입으로 세지 않는다 |

- **시작 준비 시간**은 `h_plan`이다. 계획을 처음 확정하기까지 걸린 시간이다.
- **첫 가치**는 `h_run`이다. 처음으로 실행을 끝낸 때다.
- 시간은 달력 위의 경과 시간이다. 일한 시간이 아니다. 실제로 손을 쓴 시간은 §2에 사람이 적는다.

**둘째 표: 첫 28일 중 쓴 날의 수(`days_used_28d`)**

[주간 사용량](usage-weekly.md)과 같은 "사용"(게시, 확정, 작업지시, 실행, 원장, 구매)을 날짜로 센다. 만든 날로부터 하루가 지나기 전의 일은 세지 않는다.

## 2. 사람이 적는 것

공장마다 다음 표를 운영 기록(공장 이름이 아닌 프로젝트 ID로)에 남긴다. 판정 때 §1의 결과와 합친다.

| 프로젝트 ID | 기간(월) | 시작 준비에 함께 쓴 시간(시간) | 교육 시간(시간) | 지원 요청 수 | 배포·지원 비용(월, 원) | 메모 |
|---|---|---|---|---|---|---|

- **시작 준비에 함께 쓴 시간:** 우리 쪽 사람이 그 공장의 자료 옮기기와 설정을 도운 시간이다.
- **교육 시간:** 화면 안내와 시연에 쓴 시간이다.
- **배포·지원 비용:** 그 공장에 나눠 붙는 서버·백업·저장소 비용과 지원에 쓴 시간을 금액으로 바꾼 것이다.

## 3. 돌리는 때

- 파일럿 공장이 들어오면 매주 [주간 사용량](usage-weekly.md)과 함께 뽑는다.
- 판정 1 전에는 공장마다 `h_plan`, `h_data_in`, `days_used_28d`와 §2의 표를 한 줄로 모은다.
- 매일 백업([backup-restore](backup-restore.md) §7)과 시각이 겹치지 않게 돌린다.
