# CI가 다시 돌리지 않는 것

> **현행 문서** · 2026-11-22. 워크플로의 실행 조건이나 건너뛰는 규칙을 바꾸면 같은 변경에서 고친다.

검사는 줄이지 않고, 같은 코드로 이미 통과한 검사를 다시 돌리지 않는다. 개발을 막는 조건도 PR에 필요한 것만 남긴다.

## 1. 언제 무엇이 도나

| 때 | 도는 것 |
|---|---|
| PR(push할 때마다) | 경로 조건에 걸린 워크플로. E2E는 이미 통과한 명세 파일을, 백엔드는 이미 통과한 테스트 클래스를 빼고 돈다(§2, §3) |
| PR을 `main`에 merge | 작성자 표기(`commit-attribution.yml`)만. 나머지는 PR에서 merge할 코드로 이미 돌았다 |
| 매일 밤 `main` | `backend`, `frontend`, `compute`, `sequence-optimizer`, `mock-e2e`, `browser-e2e` 전부. E2E도 빼는 것 없이 다 돈다 |
| 매주, 또는 손으로 | `security.yml`의 의존성 감사(npm audit, OWASP) |
| 손으로(`workflow_dispatch`) | 그 워크플로 전부, 빼는 것 없이. 릴리스 후보는 이렇게 돌린다([점검표](../status/RELEASE-CHECKLIST.md)) |
| `release-validation/**` push | 예전처럼 경로 조건대로 |

밤 실행은 고르기로는 볼 수 없는 것을 잡는다. 날짜에 따라 바뀌는 테스트, 새 브라우저, 따로 통과한 두 PR이 합쳐진 결과가 그렇다. 밤 실행이 실패하면 다음 PR보다 먼저 고친다.

## 2. 이미 통과한 E2E 명세 건너뛰기

`flowmat_frontend/e2e/support/already-passed/`가 한다. 모의 E2E(`mock-e2e.yml`)와 실 API E2E(`browser-e2e.yml`)가 같은 방법을 쓴다.

**같은 코드의 뜻.** 명세 파일 하나가 지난번에 통과했고, 아래가 모두 그때와 같으면 뺀다.

- 명세 파일과, 그 파일이 import하는 파일 모두(`e2e/support/mockApi.ts` 등, `../src/…`도 따라간다).
- 그 명세가 돌 때 브라우저가 받아 간 빌드 파일들의 원본 파일 모두.
  - 빌드가 산출 파일마다 원본 파일 목록을 적는다(`vitePlugin.js`, `E2E_CHUNK_MAP`).
  - `vite preview`가 받은 요청을 시각과 함께 적는다(`E2E_ASSET_LOG`).
  - 기록기가 테스트마다 시작·끝 시각을 적는다(`reporter.ts`, `E2E_PASSED_LOG`).
  - 이 셋을 맞춰 본다. 한 테스트가 돌던 때 받은 파일은 그 테스트의 것이다. 테스트 사이에 받은 파일은 앞뒤 테스트 모두의 것으로 친다.
- 모든 테스트에 영향을 주는 파일: `package-lock.json`, `playwright.config.ts`, `vite.config.js`, `index.html`, 기록 도구 자신.
- 워크플로 파일. 실 API는 여기에 백엔드(`flowmat_backend/`)와 `scripts/` 전체도 더한다. 백엔드를 바꾸면 실 API 명세는 모두 다시 돈다.

**다시 도는 것.**

- 위 중 하나라도 바뀐 명세.
- 지난번에 실패한 명세.
- 재시도로만 통과한 명세(불안정한 것으로 본다).
- 받은 파일을 원본으로 되짚지 못한 명세.
- 기록이 30일 지난 명세.
- 새 명세.

전역 CSS(`src/index.css`)는 첫 화면이 싣는 파일이라 바꾸면 모든 명세가 다시 돈다.

**조각.** 모의 E2E는 세 조각으로 돈다. 명세 파일은 이름만으로 조각에 나뉜다(`select.mjs plan --shard`). 그래서 실패한 조각 하나만 다시 돌려도 같은 파일들을 맡고, 실패했던 명세를 다시 돌린다. 조각은 파일을 통째로 맡는다(`E2E_FILE_SHARDS`). 한 파일의 테스트가 모두 통과했는지 그 조각이 알아야 하기 때문이다.

**기록.** 통과 기록은 Actions 캐시에 있다(`e2e-passed-mock-<조각>-…`, `e2e-passed-real-…`). PR은 자기 PR의 최신 기록을 읽고, 없으면 `main`의 밤 실행 기록을 읽는다. 기록을 지우면 다음 실행은 모든 명세를 돌린다. 건너뛴 명세는 작업 요약(Step summary)에 이름으로 나온다.

**실 API.** 명세 단계를 두 조각(`browser-e2e (1/2)`, `(2/2)`)으로 나눠 동시에 돌린다. 조각마다 백엔드와 DB가 따로 있고, 명세는 데모 프로젝트에 자기 자료를 만들어 쓰므로 다른 조각이 필요 없다. 단계는 실행 시간(약 120초씩)으로 나눴고, 단계를 더하면 시간이 적은 조각에 넣는다. 남은 명세가 하나도 없으면 `browser-e2e` job은 백엔드를 띄우지 않는다. `plan` job이 그렇게 정하고, `browser-e2e`는 skipped로 남는다. 이 skipped는 같은 코드의 통과 기록이 있다는 뜻이다.

**전부 돌리기.** 손으로 돌리거나 밤 실행을 기다린다. 이 두 실행은 기록을 읽지 않고 모든 명세를 돌린 뒤 새로 적는다.

## 3. 백엔드

**컨텍스트 순서.**

- 테스트 클래스는 Spring 컨텍스트가 같은 것끼리 이어서 돈다(`SpringContextClassOrder`, `src/test/resources/junit-platform.properties`).
- 컨텍스트 캐시는 4개까지만 둔다(`build.gradle`, 메모리와 DB 연결 때문).
- 이름순으로 돌면 `@MockitoBean`이 있는 클래스가 사이사이 끼어 공용 컨텍스트가 밀려났다. 그래서 설정 23개에 컨텍스트를 42번 띄웠고, 한 번에 2~4초씩 들었다(2026-11-22).
- 묶으면 설정마다 한 번만 띄운다.

**이미 통과한 테스트 클래스 건너뛰기.** `src/test/java/org/myweb/flowmat/testimpact/`가 한다. 통합 테스트 338개가 기능 이름으로 최상위 패키지에 있어, 패키지로는 어느 모듈에 엮였는지 알 수 없다. 그래서 테스트 클래스마다 실제로 실행된 클래스를 잰다.

- **기록**(`TestImpactListener`, `-PtestImpact.record`).
  - 클래스가 시작하고 끝날 때 JaCoCo 에이전트의 데이터를 받고 비운다.
  - 그 사이에 실행된 프로젝트 클래스(`org/myweb/flowmat/…`)와 각 클래스 파일의 해시를 `build/test-impact/records/<클래스>.json`에 적는다.
  - 그 클래스가 띄운 Spring 컨텍스트도 그 클래스의 몫이다.
  - 받은 데이터는 `exec/`에도 남겨 커버리지가 모두 센다.
- **고르기**(`TestImpactFilter`, `-PtestImpact.previous=<지난 기록>`). 지난번에 통과했고 실행한 클래스가 모두 그대로인 테스트 클래스를 뺀다.
- **모두 다시 도는 때.**
  - 리소스(마이그레이션, 설정), 빌드 파일, 디스크에서 읽는 고정 입력, 테스트 클래스 경로의 라이브러리가 바뀌었을 때(키 `testImpact.key`).
  - 모든 테스트에 닿는 클래스가 바뀌었거나 새로 생겼을 때. 기록할 때 적은 전체 클래스 목록(`classes.json`, 클래스 파일마다 해시)과 비교한다. Spring 설정과 `@ConfigurationProperties`, `@ControllerAdvice`, 필터·인터셉터·리스너·`BeanPostProcessor`·러너, `@Bean`·`@EventListener`·`@Scheduled`·`@PostConstruct` 메서드, JPA 매핑, Jackson 컴포넌트, 테스트 확장, Java 마이그레이션, 이 도구 자신이 그렇다.
  - 어떤 프로젝트 클래스든 지워졌을 때.
  - 이유는 `build/test-impact/run-all.txt`에 적고 작업 요약에 나온다(예: `…/WebSocketConfig changed`).
- **늘 도는 것.** `FlowMatSmokeTest`가 늘 돈다. 무엇을 빼든 공용 컨텍스트를 띄우고 스키마를 검증한다.
- **커버리지.** 뺀 클래스는 지난 기록과 exec 파일을 이번 기록으로 옮긴다. 그 클래스가 실행한 클래스는 그대로이므로, 커버리지 기준(줄 45%, 분기 30%)은 빼지 않은 것처럼 센다.
- **CI**(`backend.yml`).
  - PR은 캐시(`backend-test-impact-…`)의 최신 기록으로 고른다. 없으면 `main`의 밤 실행 기록을 쓴다.
  - 밤 실행과 손으로 돌린 실행은 전부 돌리고 새로 적는다.
  - 몇 개를 돌리고 몇 개를 뺐는지 작업 요약에 나온다.
- **로컬.** 속성 없이 돌리면 지금처럼 전부 돈다.
- **한계.** 클래스 단위다. 큰 서비스 클래스의 메서드 하나를 바꿔도 그 클래스를 실행한 테스트는 모두 다시 돈다. 테스트끼리 DB 자료로 몰래 기대고 있으면, 빼고 돌릴 때 드러날 수 있다(밤 실행은 전부 돈다).

## 4. 의존성 감사

- PR merge의 조건이 아니다. NVD(미국 NIST 취약점 DB)의 키나 장애가 개발을 막지 않게 하려는 것이다.
- 매주와 손으로 돌린다. 검사가 실패하는 것은 검사를 돌리지 못했을 때뿐이다.
  - NVD에 닿지 못했거나 키가 거절되면 오류 제목이 `Vulnerability data unavailable`이고, 발견이 아니라고 적는다.
  - 발견은 다음 단계가 심각도별로 세어 요약에 적는다. 높음·치명이 있으면 경고를 단다.
- 릴리스 후보는 [점검표](../status/RELEASE-CHECKLIST.md) 6번으로 판정한다. 외부 오류로 돌지 못했으면 그렇게 적고, 배포 결정 전에 다시 돌린다.
