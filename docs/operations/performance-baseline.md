# 성능 기준선

> **현행 문서** · 측정 2026-11-14(`main` V134, 로컬 `dev` 프로필), 같은 날 읽기를 묶은 뒤 다시 쟀다(§4). 다시 재면 §5 기록 표에 줄을 더한다.

[월간 계획](../status/MONTH-PLAN-2026-11-16.md) 3주차 4번이다. 계산을 따로 떼어(`flowmat-compute`, 나아가 Rust) 빨라질 곳이 있는지를 숫자로 판단하려고 잰다. 대상은 계산이 무거워 보이는 세 가지다. 다단계 BOM 전개, 간이 MRP, 시뮬레이션 실행이다.

## 1. 재는 법

```bash
node scripts/perf/baseline.mjs
```

떠 있는 백엔드(기본 `http://127.0.0.1:8080/api`)에 새 프로젝트를 만들고, 그 안에 정해진 입력을 짓는다. 다른 프로젝트는 건드리지 않는다. 각 호출을 5번 데운 뒤 30번 재고 최소·중앙값·95%·최대를 JSON으로 낸다. `RUNS`, `WARMUP`, `FLOWMAT_API`로 바꾼다.

| 계산 | 입력 | 호출 |
|---|---|---|
| 다단계 BOM 전개 | 제품 1 → 조립품 5 → 부분 조립품 25 → 자재 100. 부모마다 자식을 2개씩 쓴다. 승인된 BOM 31개 | `GET /boms/{제품 BOM}/explosion?quantity=10` |
| 간이 MRP | 위 트리에 승인된 작업지시 40건(제품과 조립품 5종, 수량 1~7). 자재 100종마다 재고 50 | `GET /material-requirements?projectId=` |
| 시뮬레이션 실행 | 공정 60개를 잇고 10개마다 옆 가지를 둔 워크플로(연결 64개)를 발행 | `POST /flow-runs/graph`, `runType: simulation` |

SQL 문 수는 로컬 Compose DB에 잠시 `log_statement = 'all'`을 켜고, 호출 한 번 전후의 로그 줄을 세어 구했다. 끝나면 되돌린다.

## 2. 결과(2026-11-14)

기계: 클라우드 컨테이너, Xeon 2.10GHz 4코어, 메모리 16GB. 백엔드·Postgres·Redis가 같은 기계에 있다.

| 계산 | 결과 크기 | 최소 | 중앙값 | 95% | 최대 | 호출 한 번의 SQL 문 |
|---|---|---|---|---|---|---|
| 다단계 BOM 전개 | 줄 130 | 567 ms | 629 ms | 765 ms | 772 ms | **750** |
| 간이 MRP | 줄 130 | 1,439 ms | 1,599 ms | 1,749 ms | 1,831 ms | **2,193** |
| 시뮬레이션 실행 시작 | 단계 60 | 11 ms | 17 ms | 20 ms | 20 ms | (재지 않음) |

## 3. 판단

- **느린 곳은 계산이 아니라 DB 왕복이다.** BOM 전개는 줄 하나에 SQL 문 약 6개, MRP는 줄 하나에 약 17개를 보낸다. 130줄짜리 트리를 곱하고 더하는 계산은 1ms도 걸리지 않는다. 같은 입력에서 문 수가 줄 수에 비례하므로 N+1 질의다.
- **`flowmat-compute`를 따로 만들거나 Rust로 옮길 근거는 지금 없다.** 계산을 다른 프로세스나 언어로 옮겨도 같은 자료를 같은 방식으로 읽으면 시간은 그대로다. 오히려 프로세스 사이 직렬화가 더해진다.
- **다음 일은 읽기를 묶는 것이다.** 전개와 MRP가 BOM 줄·품목·단위·재고를 단계마다 한 번씩 묶어 읽게 하면 문 수가 줄 수가 아니라 단계 수(4)에 비례한다. 같은 날 그렇게 고쳤다(§4).
- **Rust 비교는 범위를 좁힌다.** 월간 계획의 "조건식 언어를 WASM으로" 비교는 DB를 읽지 않는 순수 계산이라 그대로 해 볼 수 있다. 전개·MRP는 묶어 읽기 뒤에 계산 부분만 떼어 비교한다.
- **시뮬레이션 실행 시작은 빠르다(17ms).** 발행본 스냅숏 한 덩어리를 읽어 그래프를 짓기 때문이다. 단계를 하나씩 진행하는 비용은 이 기준선에 없다.

## 4. 읽기를 묶은 뒤(2026-11-14)

계산은 그대로 두고 읽는 방식만 바꿨다.

- **단위표를 한 번만 읽는다.** `UnitConversion.table()`이 단위 마스터를 한 번 읽어, 줄마다 두 번씩 하던 단위 조회를 대신한다. 환산 규칙은 같은 코드(`UnitConverter.convert`)를 쓴다.
- **BOM 하나의 품목을 한 번에 읽는다.** 소요량 계산이 BOM의 줄을 읽은 뒤 그 품목들을 질의 하나로 읽는다. 전에는 줄마다 품목과 그 단위를 따로 읽었다.
- **한 요청이 읽은 것을 나눠 쓴다.** `BomQuery.requirementsBatch(projectId)`가 준 묶음 안에서는 같은 BOM·줄·품목·오늘 날짜를 다시 읽지 않는다. MRP는 작업지시 40건이 BOM 6개를 되풀이해 계산하므로 효과가 크다. 묶음은 그 요청 안에서만 쓴다. 요청 사이에 남기는 캐시가 아니다.
- **트리를 단계별로 미리 읽는다.** 전개는 단계마다 그 단계의 BOM들을 질의 몇 개로 읽고(`prefetch`), 그 뒤의 순회는 읽은 것만 쓴다. MRP는 필요가 닿을 수 있는 반제품의 재고·품목·BOM을 한 번에 읽는다. 다른 날짜의 개정을 지나는 팬텀처럼 미리 읽지 못한 것은 닿았을 때 읽는다.

| 계산 | 중앙값(전 → 후) | 95%(전 → 후) | 호출 한 번의 SQL 문(전 → 후) |
|---|---|---|---|
| 다단계 BOM 전개 | 629 ms → **43 ms** | 765 ms → 49 ms | 750 → **40** |
| 간이 MRP | 1,599 ms → **59 ms** | 1,749 ms → 77 ms | 2,193 → **65** |
| 시뮬레이션 실행 시작 | 17 ms → 17 ms | 20 ms → 20 ms | (바꾸지 않음) |

결과가 같은지는 세 가지로 확인했다.

- 같은 DB에 옛 코드와 새 코드를 차례로 띄워 응답을 비교했다. 기준선 프로젝트의 승인된 BOM 31개 전개, 데모 프로젝트의 전개 1개, 두 프로젝트의 MRP가 바이트까지 같다.
- `BomReadBatchingIntegrationTest`(실제 Postgres): 줄이 7배인 트리의 전개와 작업지시가 5배인 MRP가 SQL 문을 똑같이 보낸다. 옛 코드에서는 실패한다(전개 45 → 209, MRP 116 → 260).
- 전체 백엔드 테스트가 통과한다.

이로써 §3의 판단이 굳는다. 두 계산은 Java 안에서 50ms 안팎이고 남은 시간도 대부분 질의다. 따로 떼거나 Rust로 옮길 이유가 없다.
