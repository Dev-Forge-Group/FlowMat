# 개인정보 목록과 처리방침의 근거

> **현행 문서** · 확인 2026-11-24(`main` V142). 개인정보를 담는 표·칸이나 보관 방식을 바꾸면 같은 변경에서 고친다.

[로드맵](../status/ROADMAP-2026-11-23.md) §5의 8번은 파일럿·유료 공장용 배포에 이용 약관과 개인정보 처리방침을 요구한다. 이 문서는 그 근거다.

- §1: FlowMat이 실제로 어떤 개인정보를 어디에 두는지. 코드와 마이그레이션에서 읽었다.
- §3: 지금 지키지 못하는 것
- §4: 처리방침에 들어갈 항목

**법률 자문이 아니다.** 처리방침과 약관의 문안은 법률 검토를 거쳐 사람이 확정한다(§4).

## 1. 무엇을 어디에 두는가

| 표 | 칸 | 누구의 정보인가 | 누가 넣나 | 왜 |
|---|---|---|---|---|
| `users` | `user_id`, `user_name`, 닉네임, `user_email`, `user_pwd`(BCrypt 해시), `user_birth`, `user_tel`, `avatar_url`, 상태·잠금·휴면·탈퇴 시각, 로그인 실패 수 | 사용자 | 본인(가입, Google·Kakao 로그인) | 계정, 로그인, 연락 |
| `user_login_history` | `login_ip`, `user_agent`, 결과·실패 이유, 로그인·로그아웃 시각 | 사용자 | 서버 | 보안(이상 로그인 확인) |
| `face_descriptor` | 얼굴 특징 벡터(`descriptor`), 실패 수, 잠금 | 사용자 | 본인 | 얼굴 로그인. **기본은 꺼져 있다**(`APP_AUTH_FACE_LOGIN_ENABLED=false`) |
| `project_invite` | `invited_email`, 초대 토큰 | 초대받은 사람 | 프로젝트 관리자 | 초대 |
| `project_member`, `organization_member` | 사용자 ID, 역할 | 사용자 | 관리자 | 권한 |
| `worker_attendance` | 출근·퇴근 시각, 메모 | 공장의 작업자 | 작업자 본인·관리자 | 근무 시간 대조([worker-calendar](../domain/worker-calendar.md) AT) |
| `worker_labor_rate`, `labor_premium_rule` | 시급, 할증 규칙 | 공장의 작업자 | 프로젝트 소유자 | 인건비(ADR-025) |
| `worker_schedule`, `worker_rota`, `worker_shift`, `worker_day_*` | 근무 일정, 쉬는 날 | 공장의 작업자 | 관리자 | 계획(ADR-043) |
| `production_run_labor` | 실행마다 사람·분 | 공장의 작업자 | 작업자·관리자 | 실행 기록, 인건비 |
| `notification` | 알림 제목·본문 | 사용자 | 서버 | 알림 |
| `admin_user_action_log` | 관리자가 바꾼 사용자 값(전·후), 이유 | 사용자 | 서버 | 관리 감사 |
| `payment` | 금액, 결제 수단, PG 거래 ID | 결제한 사용자 | 결제 대행사 응답 | 결제 |
| Redis | 갱신 토큰(기기별), 로그인 실패 수 | 사용자 | 서버 | 세션, 무차별 대입 막기([로그인 보안](login-security.md)) |
| 첨부 저장소 | 작업 지침 첨부(사진 등) | 사진에 찍힌 사람이 있을 수 있다 | 관리자 | 작업 지침 |

공장의 생산 자료(품목, 재고, 계획, 실행)는 개인정보가 아니다. 다만 실행의 `started_by`·`finished_by`처럼 사람 ID가 붙은 칸은 그 사람을 가리킨다.

## 2. 누가 처리자인가

B2B 서비스라 정보의 주인이 둘로 나뉜다.

- **사용자 계정(`users`, 로그인 기록, 결제):** DevForge가 개인정보처리자다. 가입한 사람에게서 직접 받는다.
- **공장 작업자의 근무·시급·출퇴근:** 공장(고객사)이 근로자에게서 받아 FlowMat에 넣는다. 처리자는 공장이고, DevForge는 처리를 위탁받는 수탁자다. 계약에 위탁 조항(처리 목적, 안전조치, 재위탁 제한, 파기)을 둔다.
- 파일럿 계약 전에 사람이 이 구분을 확인한다.

## 4. 처리방침에 들어갈 항목 (초안의 뼈대)

문안은 법률 검토 뒤 사람이 확정한다. 아래 각 항목의 근거는 §1–§3이다.

1. 처리 목적: 계정과 로그인, 서비스 제공(계획·실행·재고), 보안, 결제, 알림
2. 처리 항목: 필수(아이디, 이름, 닉네임, 이메일, 전화(계정 찾기), 비밀번호 해시), 선택(생일, 사진), 자동(접속 IP, 브라우저, 로그인 시각)
3. 보유 기간: 탈퇴 후 30일(설정), 로그인 기록 1년(설정), 결제 기록(전자상거래법의 보존 기간), 백업 14일
4. 제3자 제공: 없음(법령 예외만)
5. 처리 위탁: [호스팅], [메일 발송], [결제 대행] — 배포가 정해지면 채운다(P7)
6. 국외 이전: [있음/없음](P7)
7. 파기 절차와 방법: 매일 한 번, 기간이 지난 탈퇴자의 이름·연락처·생일 등을 지우거나 바꾸고, 로그인 기록을 지운다(P1–P2). 백업에서는 14일 안에 사라진다
8. 정보주체의 권리와 행사 방법: 열람·정정(`PATCH /users/me`), 삭제(탈퇴), 처리 정지 요청 창구
9. 안전성 확보 조치: 비밀번호 BCrypt, 로그인 잠금과 갱신 토큰 재사용 감지([로그인 보안](login-security.md)), 프로젝트 격리 검사, 백업과 복원 리허설
10. 개인정보 보호책임자: [이름, 연락처]
11. 공장 작업자 정보: 고객사가 처리자이고 DevForge는 수탁자라는 설명(§2)
12. 변경 고지: 시행일과 이전 판

이용 약관은 다음을 담는다.

- 서비스 범위(파일럿·유료)
- 계정과 프로젝트 권한
- 고객 자료의 소유(공장 자료는 고객 것)와 서비스 종료 시 내보내기
- 가용성과 백업의 한계
- 금지 행위
- 요금과 해지
- 책임 제한
- 분쟁 해결

파일럿 계약서와 함께 법률 검토를 받는다.
