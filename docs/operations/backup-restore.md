> **현행 문서** · 확인 2026-11-14(`main` V134). 절차나 스크립트를 바꾸면 같은 변경에서 고친다.

[월간 계획](../status/MONTH-PLAN-2026-11-16.md) 3주차 1번이다. 백업이 실제로 되살아나는지를 정해진 절차로 확인한다. 덤프를 만드는 데서 끝나지 않는다. 빈 DB에 복원하고, 앱을 그 위에 띄우고, 두 여정(구매·창고, 생산·품질·LOT)의 재고·원장·금액이 복원 전과 같은지 본다.

## 1. 한 번에 돌리기

저장소 루트에서 실행한다. Docker, 로컬 Compose DB(`flowmat_backend/.env`), JDK 21이 있어야 한다.

```bash
scripts/ops/restore-rehearsal.sh
```

원본 DB는 읽기만 한다. 복원용 컨테이너는 확인할 수 있게 남겨 둔다. `CLEANUP=1`이면 끝에 지운다. 포트와 이름은 스크립트 머리말의 환경 변수로 바꾼다. 기본값은 DB 5444, Redis 6390, 앱 8091이다.

두 여정의 자료가 DB에 있어야 5단계가 뜻을 가진다. 없으면 먼저 실 API 브라우저 테스트를 돌린다.

```bash
cd flowmat_frontend
```


## 2. 스크립트가 확인하는 것

| 단계 | 하는 일 | 통과 기준 |
|---|---|---|
| 1 | 원본 컨테이너에서 `pg_dump -Fc`. 덤프와 그 sha256을 `flowmat_backend/build/restore-rehearsal/`에 둔다. 원본 지문을 뜬다 | 덤프가 만들어짐 |
| 2 | 새 `postgres:16` 컨테이너를 띄우고, 비어 있는지 확인한 뒤 `pg_restore --exit-on-error --no-owner` | 오류 0 |
| 3 | 복원본의 지문을 떠서 원본과 `diff` | 한 글자도 다르지 않음 |
| 4 | 같은 커밋의 jar(`bootJar`)를 `dev` 프로필로 복원본 위에 띄운다. Redis는 따로 띄운 빈 것을 쓴다 | `Successfully validated N migrations`, `Schema "public" is up to date`. `Migrating schema`가 나오면 실패 |
| 5 | `demo-owner`로 로그인해 두 여정의 프로젝트마다 `GET /api/inventories`의 수량 합을 지문의 DB 합과 비교 | 모든 여정 프로젝트에서 같음 |
| 6 | 앱이 뜨고 읽은 뒤 지문을 다시 떠서 마이그레이션·여정 내용·프로젝트 합계를 원본과 비교 | 같음(로그인 기록 같은 인증 표는 비교하지 않는다) |

지문(`scripts/ops/restore-fingerprint.sql`)은 읽기만 하는 질의다.

- **마이그레이션:** 적용된 수, 마지막 버전, 체크섬 합.
- **표마다 행 수:** `public`의 모든 표.
- **여정 표 15개의 전체 내용 해시:** 재고, 원장, LOT, 계보, 구매 주문·줄·입고·반품, 창고 작업, 작업지시, 할당, 실행, 실행 항목, 검사, 부적합. 행을 글자로 바꿔 정렬한 뒤 md5를 낸다.
- **프로젝트마다 합계:** 재고, 예약, 원장, 이동 수, 구매 금액.

시간대는 UTC로 고정해 두 DB의 글자가 같게 나온다.

## 3. 백업에 들어가지 않는 것

- **첨부 파일.** 작업 지침 첨부는 DB가 아니라 `app.storage`에 있다. 기본값은 `./uploads`이고, S3면 그 버킷이다. DB 덤프와 같은 시점에 따로 복사해야 한다. 이 리허설은 첨부를 확인하지 않는다.
- **Redis.** 캐시와 로그인 제한 계수만 있다. 비워도 앱이 다시 채운다. 복원본을 띄울 때도 빈 Redis를 쓴다.
- **환경 변수와 비밀값.** `.env`나 운영 환경의 설정은 덤프 밖이다. 복원한 DB에는 같은 `JWT_SECRET`이 있어야 기존 토큰이 맞는다. 없으면 다시 로그인하면 된다.

## 4. 실제로 복원할 때

리허설과 같은 순서를 사람이 밟는다. 운영 DB 덮어쓰기는 이 문서의 범위가 아니다. 새 DB에 복원하고 확인한 뒤 연결을 바꾼다.

1. 덤프의 sha256을 확인한다.
2. 빈 DB를 만들고 `pg_restore --exit-on-error --no-owner --role=<앱 사용자>`로 복원한다.
3. 같은 커밋의 앱을 띄워 Flyway가 "up to date"인지 본다. 더 새 앱이라면 마이그레이션이 적용되는 것이 정상이다. 이것은 업그레이드 리허설(3주차 2번)의 일이다.
4. 지문 질의로 원본 시점의 기록과 비교한다. 원본에 지문 기록이 없으면 프로젝트 합계 줄만이라도 확인한다.
