# 구매 발주 (Purchase order)

상태: **로컬 구현(2026-10-24, 2fm, V106 커밋 전; 단가 V108, 공급처 목록 V109도 커밋 전).** 결정은 [ADR-027](../architecture/adr/ADR-027-purchasing.md)(사용자 위임 2026-10-24). 새 컨텍스트 `purchasing`.

## 왜 필요한가

[재주문 목록](stock-alert.md)과 [열린 작업지시 자재 소요](material-requirements.md)는 무엇을 얼마나 사야 하는지 알려 주지만, 주문을 냈는지와 무엇이 들어왔는지는 남지 않았다. 발주서는 주문과 입고를 기록하고, 받은 재고가 어느 발주의 것인지 원장에 남긴다.

## 모델

`purchase_order` (프로젝트별)

| 열 | 뜻 |
|---|---|
| `order_number` | `PO-0001`부터, 프로젝트 안에서 유일, 다시 쓰지 않음 |
| `supplier_name` | 공급처 100자. 공급처 목록이 없으면 자유 글, 있으면 활성 공급처의 목록 표기(PO20). 공급처 이름을 바꿔도 그대로 |
| `status` | `draft`·`ordered`·`received`·`closed`·`cancelled` |
| `expected_date`, `note` | 예정일(선택), 메모 500자 |
| `deliver_to` | 도착 장소 100자(V116, 2gh, PO39). 위치 목록이 있으면 활성 목록 위치의 표기 |
| `ordered_by/at`, `ended_by/at`, `end_reason` | 주문한 사람, 다 받거나 닫거나 취소한 사람과 사유(닫기·취소는 사유 필수, DB 제약) |
| `approved_by/at` | 소유자의 승인(V113, 2gc, PO34). 초안을 고치면 지워짐 |

`purchase_order_line`: 줄 번호, 품목, 수량·받은 양(품목의 재고 단위, 소수 4자리, 받은 양 ≤ 수량), 예정일, 메모, 단가(재고 단위당, 선택, V108). 한 발주서에 같은 품목 한 줄.

`purchase_receipt`: 입고 한 줄. 줄, requestId(함께 받은 줄끼리 같음), 양, 들어간 재고 행, 위치, LOT 번호, 받은 사람·시각.

`supplier`(V109, 2fv): 프로젝트의 공급처. 이름(100자, 프로젝트 안에서 대소문자를 무시하고 하나), 연락처(200자), 납기(0–365일, 선택), 메모(500자), 활성, version. 지우지 않고 끈다.

`purchase_order_date_change`(V110, 2fw): 주문 뒤 옮긴 예정일 하나. 발주서, 줄(없으면 발주서의 예정일), 전·후 날짜, 사유 500자, 누가·언제. 고치거나 지우지 않는다.

`purchase_return`(V111, 2fz): 공급처로 돌려보낸 것 하나. 발주서, 줄, requestId(발주서 안에서 하나), 양, 나간 재고 행과 그때의 위치·LOT 번호, 사유 500자, 누가·언제. 고치거나 지우지 않는다.

`supplier_item`(V112, 2ga): 품목의 평소 공급처. 프로젝트·품목마다 하나, 공급처, 공급처가 부르는 품목 코드 100자, 공급처의 단가(재고 단위당, V115, PO38), version, 누가·언제.

`purchase_setting`(V113, 2gc): 프로젝트의 구매 설정. 승인 한도(없으면 승인 없음), version, 누가·언제.

## 화면

재고 → **Purchasing** 탭
- 목록: 번호, 공급처, 상태, 줄 수, 예정일. **Status**로 거른다
- 고른 발주서: 제목 `PO-0001 · Mill Co · ordered`, 줄 `FLOUR · 4 of 10 kg received`, 버튼 **Edit**·**Order**(초안), **Receive**(주문), **Close**(일부 받은 주문), **Cancel order**(받은 것이 없을 때), **Print**(늘, PO16). 사유는 확인 창으로 묻는다. 입고 줄 `2041-09-02 10:00 · FLOUR 4 at WH-A · by kim`
- 주문한 발주서의 **Change dates**(2fw): **Order expected**와 남은 줄마다 **FLOUR expected**, **Reason**, **Save dates**. 바뀐 것이 없으면 `Change a date first.`, 사유가 없으면 `Give a reason for the new dates.` 고른 발주서 아래 **Date changes**: `2041-09-12 10:00 · order 2041-09-10 → 2041-09-15 · Supplier delayed · by kim`, 줄은 `FLOUR none → 2041-09-14`

- 공급처가 갚을 반품(PO47)은 **Returns** 줄 끝에 `· credit due 10`(단가 없으면 `· credit due (no price)`)과 **Record credit**: **Amount credited**(처음엔 갚을 양 × 줄 단가), **Credit note**, **Save credit**. 저장 전 `Enter the amount credited: 0 or more with at most four decimals.` 남긴 뒤 `· credited 9.5 · CN-12 · by kim`. 발주서에 `Credit due 10 (1 return without a price)`(모두 단가 없으면 `Credit due on 2 returns without a price`). 공급처 화면 **Credit due** 표(PO48)

## 대변 저장 대기 중 새 입력 보존 (2026-11-10)

대변의 최초 기록·변경·취소가 완료되어도, 응답을 기다리며 고친 금액·대변표 번호·사유는 보존한다. 제출할 때의 폼과 현재 폼이 같은 경우에만 성공 후 닫는다. Close credit 뒤 다른 반품에 연 폼의 입력을 이전 응답으로 바꾸지 않는다.

최초 기록 POST가 성공한 동안 같은 반품의 새 입력을 작성했다면, 그 입력을 유지한 **Change credit** 폼으로 이어진다. 다음 저장은 사유를 요구하고 기존 PUT 변경 API를 사용한다. 새 입력을 다시 최초 기록 POST로 보내 이미 남긴 대변과 충돌하지 않도록 한다. 금액 문자열과 PO47/PO52의 검증·이력·동일 요청 재실행 계약은 유지한다.

응답이 유실되면 같은 최초 기록 본문을 다시 전송할 수 있다. 다른 금액·번호를 같은 최초 기록으로 덮어쓰거나, 자동으로 쓰기를 재시도하지 않는다. 이 UI 보완은 새로운 요청 키나 회계 정책·DB 변경을 추가하지 않는다. 브라우저 회귀는 지연 응답의 입력 보존과 다음 변경 완료, 수정 없는 정상 닫기, 최초 기록 응답 유실 후 동일 본문 재시도, 다른 반품 전환을 구별한다.
