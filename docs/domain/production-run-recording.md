# 생산 실행 기록의 재전송

상태: **구현함(2026-11-14).** [월간 계획](../status/MONTH-PLAN-2026-11-16.md) 2주차 여정에서 나온 결함을 고쳤다.
관련: [재고 할당](stock-allocation.md) · [LOT 유통기한](lot-expiry.md) "여러 LOT에 나눠 투입" · [끝난 실행의 보정](production-run-correction.md)

---

## 1. 풀려는 문제

실행 상세에서 투입·산출을 기록하면(`POST /production-runs/{id}/items`) 재고가 움직이고 LOT 계보가 이어진다. 서버는 기록했는데 응답이 브라우저에 닿지 않으면, 화면은 실패로 보이고 사람은 다시 누른다. 이 요청에는 열쇠가 없어서 같은 투입이 두 번 기록되고 재고도 두 번 빠졌다. 여러 LOT에 나눠 투입(`POST /production-runs/{id}/inputs/fefo`)도 같았다.

구매 입고, 창고 작업, 재고 이동, 할당된 재고 옮기기는 이미 `requestId`로 이 문제를 막는다. 실행 기록에만 빠져 있었다.

`RunItemRequestReplayIntegrationTest`가 고치기 전 동작을 재현한다. 같은 요청을 두 번 보내면 새 항목이 하나 더 생기고 재고가 두 번 빠졌다.

## 2. 규칙

| # | 규칙 | 거절 |
|---|---|---|
| RR1 | 기록 요청은 `requestId`(앞뒤 공백을 뺀 1~100자)를 실을 수 있다. 실은 기록은 그 열쇠를 `production_run_item.request_id`에 남긴다. 열쇠가 없는 요청은 전과 같다 | 400: 빈 열쇠, 100자 초과, PostgreSQL이 저장할 수 없는 글자 |
| RR2 | 같은 실행에 같은 열쇠로 같은 내용을 다시 보내면 처음 기록한 항목을 지금 모습 그대로 돌려주고, 재고·원장·할당·계보는 움직이지 않는다. 그사이 실행이 끝났거나 항목이 취소됐어도 그대로 돌려준다. "같은 내용"은 품목, 방향, 재고 행, 계획·실제 수량(값으로 비교), 단위, 그리고 요청이 지정한 공정·포트다 | 409: 같은 열쇠에 다른 내용. 새 기록에는 새 열쇠를 쓴다 |
| RR3 | 여러 LOT에 나눠 투입은 요청 하나에 열쇠 하나다. 나눠 기록한 항목마다 같은 열쇠와 순번(`request_part`, 1부터)을 남긴다. 다시 보내면 같은 항목들을 순번대로 돌려준다. 같은 품목·공정이고 품목 단위로 바꾼 합이 같으면 같은 요청이다(8000 g = 8 kg) | 409: 다른 품목·양. 한 건 기록의 열쇠를 나눠 투입에 쓰거나 그 반대로 쓴 경우(한 건은 순번 0) |
| RR4 | 열쇠는 실행 안에서만 뜻이 있다(`(production_run_id, request_id, request_part)`가 유일). 다른 실행에 같은 열쇠를 써도 서로 상관없다 | |

다시 보낸 요청의 확인은 실행 잠금 아래에서 한다. 같은 요청 두 개가 동시에 와도 하나만 기록된다.

## 3. 화면

실행 상세의 **Record**와 **Split over LOTs (FEFO)**는 `createStockCommand`로 요청을 보낸다(재고 출고·이동 화면과 같다). 응답을 받기 전에는 내용이 같은 요청에 같은 열쇠를 다시 쓰고, 응답을 받으면 열쇠를 버린다. 네트워크 오류나 5xx면 결과를 모른다고 알리고, 값을 바꾸기 전에 같은 값으로 다시 누르라고 한다.

## 4. 검증

- `RunItemRequestReplayIntegrationTest` 3건(실제 Postgres)
  - 한 건 기록: 다시 보냄 → 같은 항목, 재고·원장·항목 그대로. 같은 열쇠에 다른 양·다른 재고 행 → 409. 새 열쇠와 열쇠 없음은 새 기록. 취소된 항목을 다시 보냄 → 취소된 그대로 돌려줌
  - 나눠 투입: 8000 g → 두 LOT. 다시 보냄, 8 kg으로 다시 보냄 → 같은 항목들. 9 kg → 409. 한 건 기록과 열쇠를 바꿔 쓰면 409
  - 저장할 수 없는 열쇠 → 400이고 아무것도 바뀌지 않음
- `RunInputAllocationServiceTest`: 나눠 기록한 항목의 순번이 1, 2
- 실 API 브라우저 테스트 `production-quality-live.spec.ts`: 투입 기록의 응답을 잃은 뒤 다시 눌러도 한 번만 기록된다. 재고·할당·원장·계보·원가가 맞는다

## 5. 같은 여정에서 고친 것: 비워 둔 산출 수량

실행 상세의 **Finish**에서 `Actual output qty`를 비우면, 칸에는 기록한 산출(20)이 회색 글씨로 보였지만 서버에는 수량 없이 끝났다(`actual_output_qty` null). 그러면 개당 원가가 비고, 작업지시의 생산량(끝난 실행들의 `actual_output_qty` 합, [준비 점검](work-order-readiness.md))에 0으로 들어갔다.

이제 칸이 비면 칸에 보이던 값으로 끝낸다. 값은 그 실행이 기록한 제품 산출이고, 없으면 계획량이다. 부산물 안내(`finishOutput`, [bom-by-products.md](bom-by-products.md))가 쓰는 값과 같다. 확인 창은 `Finish this run with 20 made?`처럼 그 수를 묻는다. 서버의 자동 계산은 [보정 문서](production-run-correction.md) Q6대로 아직 하지 않는다. 화면이 보인 수를 보낼 뿐이다.

- `byproduct-finish.spec.ts`(모의 API): 칸을 비우고 끝내면 `{ actualOutputQty: 16 }`을 보내고, 확인 창에 16이 나온다
- `production-quality-live.spec.ts`: 화면에서 칸을 비우고 끝낸 실행의 `actualOutputQty`가 20이고, 개당 원가가 1이다
