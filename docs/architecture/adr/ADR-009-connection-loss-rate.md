# ADR-009: 연결 손실률(lossRate) 적용

작성일: 2026-10-17

## 상태

**Accepted (2026-10-17, 사용자 결정 "Accept as recommended"). 로컬 구현 2ei(2026-10-17, 2026-10-18 `9500678`에서 커밋).** 같은 날 사용자 요청("Loss rate ADR draft")으로 Proposed 초안을 썼고, 사용자가 권장안 그대로 수용 기준 8개를 닫았다. [ADR-008](ADR-008-quantity-split.md)이 "결정하지 않은 것"으로 넘긴 손실률(`lossRate`) 적용을 정한다. 흐름률(`flowRate`)·지연(`delayTimeSec`)·개수 단위의 정수 처리는 이 ADR 밖이다.

근거: [ADR-008](ADR-008-quantity-split.md) 결정 7·12와 S4, [연결 계약](../../domain/process-port-connection-contract.md) PC-14·GR-03·GR-07·GR-08·GR-24·GR-31, [현재 기능](../../status/CURRENT_CAPABILITIES.md) FM-FLOW-002("지연·손실률 미적용"), [ADR-003](ADR-003-resource-port-contract.md) 결정 5(발행 snapshot은 실행 중 바뀌지 않음), [실행 모델](../execution-model.md) §6·§8.

## 배경 (2026-10-17 코드·개발 DB 기준)

| # | 지금 동작 | 근거 |
|---|---|---|
| L1 | `process_connection.loss_rate`는 `numeric(5,4)`이고 기본값은 0이다(V1). 저장 검사는 절댓값 9.9999 이하와 소수 4자리만 본다. 그래서 음수와 1 이상도 저장된다 | `ProcessConnectionServiceImpl`(`MAX_LOSS_RATE`), PC-14 |
| L2 | 편집기 입력란은 라벨이 **Loss %**인데 `min 0`·`max 1`·`step 0.01`이다. 라벨은 퍼센트, 입력 범위는 비율이라 뜻이 엇갈린다 | `ConnectionInspector` |
| L3 | 실행은 손실률을 읽지 않는다. 연결을 지난 수량은 보낸 수량 그대로다(Split은 그 몫, Join은 도착의 합) | GR-04·GR-24·GR-31, FM-FLOW-002 |
| L4 | 발행 snapshot에는 연결의 `lossRate`가 이미 들어 있다. snapshot `schemaVersion`은 지금 모든 발행본이 1이다 | `WorkflowRevisionService`(`SCHEMA_VERSION`) |
| L5 | 개발 DB(5434)에서 연결 5건·발행본 55건 가운데 손실률이 0이 아닌 것은 없다 | 2026-10-17 조회 |
| L6 | 포트(`process_io.loss_rate`)에도 같은 열이 있지만 entity가 읽지 않는다. BOM `scrap_rate`는 승인 때 "not supported yet"로 거절한다 | V1, `BomApprovalServiceImpl` |
| L7 | 그래프 실행 단계는 스냅샷만 나른다. 재고·생산 기록은 생산 실행이 따로 움직인다 | [실행 모델](../execution-model.md) §6·§8 |

L3이 이 결정의 이유다. 그림에 이송 손실 2%를 적어도 실행 기록에서는 전량이 도착하고, Split·Join으로 수량을 맞춰도 손실은 어디에도 남지 않는다. L1·L2 때문에 지금 저장된 값의 뜻도 분명하지 않다.

## 선택지

### 1. 어디서 빼는가

| 안 | 내용 | 좋은 점 | 약점 |
|---|---|---|---|
| A. 연결을 지날 때 | 그 연결로 보낸 수량 × (1 − 손실률)이 다음 단계의 입력 수량이 된다 | 손실이 그 연결(운반·이송)에 붙어 그림과 맞는다. Split 몫과 Join 도착에도 같은 규칙이 적용된다 | 손실이 있는 연결마다 기록이 하나씩 생긴다 |
| B. 받는 노드에서 | 노드에 손실률(수율)을 두고 그 노드가 받은 수량에서 뺀다 | 공정 수율과 비슷하다 | 노드에 새 필드가 필요하고, 연결의 `lossRate`는 계속 쓰이지 않는다 |
| C. 보고만 | 손실은 완료 보고가 직접 적는다(`outputSnapshot.quantity`를 줄여 보고). 지금과 같다 | 바꿀 것이 없다 | `lossRate`가 계속 뜻이 없고, 그림만 봐서는 손실을 알 수 없다 |

### 2. 이미 발행한 revision

| 안 | 내용 | 좋은 점 | 약점 |
|---|---|---|---|
| a. 새 발행본부터 | 발행할 때 snapshot `schemaVersion`을 2로 올리고, 2 이상인 발행본만 손실을 적용한다 | 이미 발행한 revision의 동작이 바뀌지 않는다(ADR-003 결정 5) | 같은 그림이라도 다시 발행해야 적용된다 |
| b. 모든 실행 | 발행 시점과 상관없이 손실률이 있으면 적용한다 | 단순하다 | 이미 발행한 동작이 바뀐다. 개발 DB에는 해당 발행본이 없다(L5) |

## 결정 (2026-10-17, 권장안 그대로)

1. **A(연결을 지날 때).** 노드에는 새 필드를 두지 않는다.
2. **뜻:** 비율, 0 이상 1 미만(0.05 = 5%). 저장 형식 `numeric(5,4)`는 그대로 쓰므로 새 마이그레이션이 필요 없다. 저장 검사를 0 ≤ r < 1로 좁힌다(음수와 1 이상은 400). 편집기는 퍼센트(0 이상 100 미만, 소수 2자리까지)로 받아 비율로 보낸다.
3. **계산:** 도착 = 보낸 수량 × (1 − r)을 소수 4자리 HALF_UP으로 반올림한다. 손실 = 보낸 수량 − 도착이다. 그래서 보낸 수량 = 도착 + 손실이 언제나 정확히 맞는다.
4. **보낸 수량:** 그 연결로 가는 수량이다. 일반 노드와 Exclusive는 출력, Split은 그 몫(ADR-008 결정 7)이다. 출력에 수인 `quantity`가 없으면 빼지 않고 그대로 보낸다.
5. **검사 순서:** 연결 용량(GR-03)과 출발 포트의 규칙·스키마는 보낸 수량으로 본다. 도착 포트의 규칙·스키마(GR-07·GR-08)는 도착 수량으로 본다. 단위 검사는 그대로다.
6. **기록:** 다음 단계 입력 스냅샷의 `quantity`는 도착 수량이고, 다른 값(`unit`·`item`·`attrs`)은 그대로다. 출발 단계에 이벤트 `transfer_loss`(`connectionId`·`targetNodeId`·`sent`·`lossRate`·`lost`·`arrived`·`unit`)를 남긴다. 새 표는 만들지 않는다. Join 도착(`arrivals[].quantity`)도 도착 수량이고, 합친 수량은 도착 수량의 합이다.
7. **도착이 0일 때:** 보낸 수량이 양수인데 반올림으로 도착이 0이 되면, Split의 0인 몫(ADR-008 결정 5)처럼 단계를 만들지 않고 `connection_filtered`(reason `loss_empty`)를 남긴다.
8. **이미 발행한 revision:** a(새 발행본부터). 발행 snapshot `schemaVersion`을 2로 올리고, 2 이상만 손실을 적용한다.
9. **발행 검사:** 오류 `LOSS_RATE_RANGE`(0 미만 또는 1 이상, 예전에 저장된 값).
10. **화면:** 인스펙터의 **Loss %**는 0 이상 100 미만이다. 실행 화면에서 손실이 있었던 갈래 단계에는 `received 98 kg · lost 2 kg`가 보인다(ADR-008 결정 11의 줄을 넓힌다).
11. **범위 밖:** 재고·생산 기록은 움직이지 않는다(L7). 포트 손실률(`process_io.loss_rate`)과 BOM 스크랩률은 이 결정 밖이다.

## 예

- 손실 2%: 100 kg → 98 kg 도착, 손실 2 kg.
- Split 70%·30%로 100 kg을 나누고 70 갈래의 연결 손실이 1%면 69.3 kg이 도착한다. Join으로 모으면 69.3 + 30 = 99.3 kg이다.
- 용량 99인 연결로 100 kg을 보내고 손실이 2%면, 용량은 보낸 100으로 보므로 409다(도착은 98이어도).
- 0.0001 kg에 손실 60%면 도착이 0.00004 → 0.0000이 되어 단계를 만들지 않는다(`loss_empty`).

## 수용 기준 (2026-10-17 사용자 확정)

- [x] 빼는 곳: **A 연결을 지날 때**
- [x] 뜻: **비율 0 ≤ r < 1, 편집기는 %로 받음**
- [x] 반올림: **도착을 소수 4자리 HALF_UP, 손실 = 보낸 − 도착**
- [x] 검사 순서: **용량·출발 포트는 보낸 수량, 도착 포트는 도착 수량**
- [x] 기록: **입력 스냅샷 `quantity` = 도착, 이벤트 `transfer_loss`, 새 표 없음**
- [x] 도착 0: **단계 없음(`loss_empty`)**
- [x] 이미 발행한 revision: **새 발행본부터(`schemaVersion` 2)**
- [x] 저장·발행 검사: **0 ≤ r < 1, `LOSS_RATE_RANGE`**

## 결정하지 않은 것

- 흐름률(`flowRate`)과 지연(`delayTimeSec`)의 실행 적용. 지연은 다음 단계의 예정 시각(`scheduledAt`)으로 옮길 수 있어 별도 ADR 후보다.
- 포트 손실률(`process_io.loss_rate`)과 BOM 스크랩률(생산 실행 쪽 규칙)
- 손실을 재고 폐기·손실 기록으로 넘길지(생산 실행 연계, [실행 모델](../execution-model.md) §6)
- 개수 단위(ea)의 정수 처리(ADR-008과 같음)

## 결과

- 좋은 점
  - 그림의 손실률이 실행 수량에 반영되고, 보낸·잃은·도착 수량이 이벤트에 남는다.
  - 이미 발행한 revision의 동작은 그대로다.
- 위험
  - 같은 그림이 발행 시점에 따라 다르게 움직인다(`schemaVersion` 1과 2).
  - 출발 포트와 도착 포트를 서로 다른 수량으로 검사하게 되어 전송 검사가 둘로 나뉜다.
  - 편집기의 단위 전환(비율 ↔ %)이 틀리면 값이 100배 달라진다. 그래서 저장 검사를 0 ≤ r < 1로 좁힌다(결정 2).
