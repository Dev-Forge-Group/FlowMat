# ADR-043: 계획 — 목표에서 거꾸로 (공통 흐름 계산과 제조 계획의 경계)

작성일: 2026-11-22

## 상태

**Accepted (2026-11-22).** [1년 개발 계획](../../status/ROADMAP-2026-11-23.md) §8 1주차의 결정이다. 세부는 2026-10-24 위임에 따라 권장안이다. 같은 날 받은 검토(11-22)의 요구를 반영했다:
- 공통 엔진은 제조에 묶이지 않는다.
- 결과에 계산 근거가 있다.
- 계획과 실행을 나눈다.
- 확정은 중복과 판 변경을 막는다.

구현은 로드맵 §8의 1~4주차 순서로 한다. 결정 4는 새 마이그레이션(추가만)을 낸다.

## 배경

- **앞으로 가는 계산은 있다.**
  - 경로 계산: `flowrun`의 `FlowRunGraph`, 라우터. Rust 커널 `routing.rs`가 같은 답이다(ADR-040).
  - 규칙: Split의 몫(ADR-008의 비율·고정·나머지, 소수 4자리 HALF_UP), 연결 손실(ADR-009), Exclusive, Join.
  - 시각: `FlowRunTiming`(ADR-041).
  - 편집기의 "Try it"은 입력에서 앞으로 따라간다.
- **포트는 이미 도메인 중립이다**(ADR-003).
  - 자원 종류: material, product, energy, water, waste, file, data, api, parameter, signal, generic.
  - 공정을 돌리는 데 필요한 것(인력·설비·계산·기술·시간)은 포트가 아니라 **실행 요건**이다. 그 모델은 ADR-003이 미뤄 두었다.
- **제조 계산도 있다**(`production`, `bom`, `inventory`, `catalog`).
  - BOM 전개(소수 4자리), 간이 MRP, 만들 수 있는 양
  - 설비의 시간당 산출·효율·달력(계획 P1), 함께 일하는 구간
  - 작업지시(`workflowId`, `bomId`, 목표 품목·수량, 설비, 계획 시작·끝), 노드별 단계 계획(분·사람)
  - 작업지시 부족분의 초안 발주(PO12)
- **없는 것.**
  - 목표에서 거꾸로 계산하기
  - 계산 근거
  - 공정별 실행 요건
  - 편집기에서 확정으로 가는 길
- **모듈 방향.** `production`은 `workflow`·`flowrun`·`bom`·`inventory`·`purchasing`·`workforce`에 기댄다. `flowrun`은 `workflow`에만 기댄다. 경로의 의미는 `flowrun`에 있다.

## 결정

### 1. 두 층과 그 경계

- **공통 흐름 계산**: `flowrun`의 공개 계약 `FlowDemand`(이름 가안).
  - 발행판 그래프와 목표를 받아, 노드·포트·연결마다 필요한 양과 그 근거를 낸다.
  - 아는 것: 노드·포트·연결, 포트 수량과 단위, 단위 환산(호출하는 쪽이 함수로 넘긴다), 연결 손실, Split·Exclusive·Join, 실행 요건의 양(결정 4).
  - 모르는 것: 재고, BOM, 설비 달력, 인력, 원가, 공급처.
- **제조 계획**: `production`의 `ProductionPlan`.
  - 포트의 품목으로 재고·할당·주문 중과 대 본다(inventory·purchasing 공개 계약).
  - 실행 요건을 설비·인력으로 푼다(catalog·workforce).
  - 시간과 병목을 놓는다(결정 5).
  - 확정을 작업지시와 초안 발주로 바꾼다(결정 7).
- **공통 층의 규칙.**
  - 이름과 결과에 재고·BOM·설비·발주 같은 제조 낱말을 쓰지 않는다.
  - 공통 층 테스트에는 제조가 아닌 그래프가 늘 하나 있다: 레코드 수가 흐르는 데이터 파이프라인(필터 손실 20%, 70/30 분할, 합류).
  - 로드맵 원칙: "하나의 산업에서 검증한 기능이라도, 공통 엔진에 들어가는 것은 다른 산업에서도 의미가 성립해야 한다."

### 2. 입력

- **판:** `revisionId`. 발행판이고, 없으면 최신 발행판이다.
  - 그리는 중인 초안은 계획하지 않는다. 확정한 작업지시가 판을 고정해야 하고(판 고정 불변식), 발행 검사가 계획의 전제(포트 계약·단위)를 보장하기 때문이다.
  - 발행하지 않은 변경이 있으면 편집기가 "발행해야 이 그림으로 계획한다"고 알린다.
- **목표:** 출력 포트(또는 End 노드로 들어가는 연결)와 수량·단위.
- **기준 시각:** 시간 계산의 시작. 기본은 지금이다.
- **배타 분기 가정**(선택): Exclusive마다 어느 갈래로 가는지(결정 3).
- **이번에는 받지 않는 것:** 목표 여럿, 고리, 수식(`formula`) 포트.

### 3. 계산: 거꾸로 전파하고, 앞으로 확인한다

**거꾸로(요구).** 목표에서 연결을 거슬러 간다.

| 만나는 것 | 규칙 |
|---|---|
| 공정 | 목표가 걸린 출력 포트의 수량이 `q_out`, 요구가 `D`면 배수 `k = D / q_out`. 입력 포트마다 요구는 `k × q_in`. 다른 출력 포트의 `k × q`는 부산물로 적는다 |
| 연결 손실 `r` | 보내야 할 양 = 도착해야 할 양 ÷ (1 − r) |
| Split | 입력 `X`에서 비율 갈래는 `X·s`, 고정 갈래는 `f`, 나머지 갈래는 `X − Σf − X·Σs`를 받는다(ADR-008). 모든 갈래의 요구를 채우는 가장 작은 `X`를 고른다. 비율 갈래는 `X ≥ d/s`, 나머지 갈래는 `X ≥ (d + Σf)/(1 − Σs)`. 고정 갈래는 `f < d`면 이 그래프로 목표를 낼 수 없다(제한 원인). 다른 갈래에 남는 양은 남는 양으로 적는다 |
| Exclusive | 조건이 갈래를 정한다. 계획은 가정을 쓴다(입력 또는 기본값 "목표로 가는 갈래"). 가정은 결과에 적는다 |
| Join | 들어오는 연결마다 Join 입력 포트의 요구가 생긴다(모두 와야 한다) |
| 같은 포트에 모이는 요구 | 같은 단위로 바꾼 뒤 더한다 |
| 고리 | 지금처럼 거절한다. 고리의 의미는 로드맵 2분기의 ADR에서 정한다 |

**앞으로(확인).**
- 거꾸로 구한 시작 입력을 기존 경로 규칙(`FlowRunGraph`, ADR-008의 반올림)으로 다시 흘려, 목표 포트에 목표 이상이 도착하는지 본다.
- 반올림으로 모자라면 시작 입력을 최소 단위(0.0001)씩 올리고, 그 일을 근거에 적는다.
- 그래서 "계획이 말한 양을 넣으면 실제 실행이 목표를 낸다"가 성립한다. 두 계산이 같은 경로 규칙을 쓰기 때문이다.

### 4. 실행 요건 (ADR-003이 미룬 모델의 최소판)

- 공정 노드마다 실행 요건 목록을 둔다: `{kind, ref?, amount, unit, per}`.
  - `kind`는 중립 낱말이다: `equipment`, `crew`, `skill`, `compute`, `time`.
  - `per`는 배수 하나당(`batch`) 또는 출력 한 단위당(`output_unit`)이다.
  - 속도는 `kind: time`의 역수로 쓴다. 예: 혼합 1회에 30분, 인원 2, 설비 `MIXER-1`.
- 공통 층은 총량만 계산한다(`k × amount`). 예: 혼합 20회 × 30분 = 600분.
- 제조 층이 `ref`를 설비·인력으로 풀고 시간을 놓는다(결정 5).
- **저장:** 새 표 `process_requirement`(새 마이그레이션, 추가만). 발행 스냅숏에 들어가고, 실행 중에는 바뀌지 않는다(ADR-003 결정 5와 같은 원칙). 노드 검사기에 "Requirements"를 둔다.
- 포트 편집 화면의 I/O Type에서 `labor`를 뺀다. ADR-003이 "실행 요건 모델을 정할 때 함께"라고 미뤄 둔 일이다.

### 5. 시간, 병목, 만들 수 있는 양 (제조 층)

- **단계 시간.**
  - 설비에 시간당 산출이 있으면: 수량 ÷ (시간당 산출 × 효율). 계획 P1과 같은 규칙이다.
  - 없으면: 실행 요건의 시간 총량 ÷ 효율.
- **놓기.**
  - 앞 단계 끝에 연결 지연을 더하고, 설비·인력의 함께 일하는 구간에 맞춘다(`FlowRunTiming`, ADR-041).
  - 같은 설비를 쓰는 단계는 겹치지 않게 차례로 놓는다.
- **제한 원인**(`limits`). 영향이 큰 것부터 적는다:
  - 재고 부족(품목, 부족량)
  - 설비 시간(가장 긴 단계, 기다린 시간)
  - 인력(사람 수, 근무 밖)
  - Split 고정 몫
  - 배타 분기 가정
- **만들 수 있는 양:** 재고만 제한으로 볼 때 목표 포트에 낼 수 있는 최대. 시작 입력마다 가용 ÷ 단위 목표당 요구의 최소로 구한다. 지금의 BOM 기준 "만들 수 있는 양"과 같은 정의를 그래프에 쓴다.

### 6. 결과와 계산 근거

| 칸 | 내용 |
|---|---|
| `requirements` | 시작 입력별 요구 수량·단위. 제조 층은 품목, 가용, 부족을 더한다 |
| `nodes` | 노드별 배수, 포트별 요구, 실행 요건 총량. 제조 층은 단계 시간과 시작·끝을 더한다 |
| `trace` | 수량마다 어떻게 나왔는지의 단계: `{at, rule, from, to, factor}`. `at`은 노드·포트·연결, `rule`은 ratio·loss·split-share·split-fixed·split-rest·join·sum·round·unit. 시작 입력 하나에서 목표까지 경로가 그대로 보인다 |
| `limits` | 제한 원인(결정 5) |
| `assumptions` | 배타 분기 가정, 반올림, 남는 양 |
| `basis` | 계산에 쓴 판과 자료의 지문: `revisionId`, 시작 입력 품목들의 가용 재고 합계와 그 시각, BOM 판, 설비·인력 달력의 판. 확정 때 다시 본다 |

- `trace`, `limits`, `assumptions`의 모양은 공통 층의 것이다. 소프트웨어 흐름 추적(요청이 어디를 거쳐 어떻게 바뀌었나)과 병목 설명에 그대로 다시 쓴다.
- 편집기는 이것으로 다음을 보인다:
  - 재료 줄을 누르면 그 경로가 캔버스에서 밝아진다.
  - 병목 단계에 표시가 붙는다.

### 7. 계획과 실행은 다르다

- **계획 조회는 읽기 전용이다.**
  - `POST /workflows/{workflowId}/plan-previews`. 저장하지 않고, 프로젝트 읽기 권한으로 된다.
  - 재고·작업지시·발주 어느 것도 바뀌지 않는다.
- **확정은 별도 명령이다.**
  - `POST /workflows/{workflowId}/plan-confirmations`. 미리 본 계획의 `basis`와 `requestId`를 보낸다.
  - 서버가 같은 입력으로 다시 계산한다. `basis`가 다르면 409와 무엇이 바뀌었는지(판, 품목별 가용, 달력)를 돌려주고 아무것도 만들지 않는다.
  - 같으면 한 트랜잭션에서 두 가지를 만든다:
    - 작업지시 초안: 판 고정, 목표 품목·수량, 계획 시작·끝, 노드별 단계 계획 분, 설비
    - 부족분의 초안 발주: PO12의 경로
  - 같은 `requestId`를 다시 보내면 같은 결과를 돌려준다(멱등).
  - 권한은 작업지시를 만들고 초안 발주를 여는 기존 권한이다.
- **재고는 확정에서도 움직이지 않는다.** 재고는 생산 실행의 투입·출력에서만 움직인다(원장 쓰기 하나, AGENTS.md). 물리 생산과 시뮬레이션을 섞지 않는다.

### 8. 단위와 정밀도

- 포트 단위와 목표·요구 단위가 다르면 기존 단위 환산(카탈로그의 단위, `WorkflowUnits`)으로 바꾼다. 환산할 수 없으면 거절하고 어느 포트인지 말한다.
- 계산 중에는 반올림하지 않는다(`BigDecimal`, `MathContext.DECIMAL128`).
- 결과는 소수 4자리다:
  - 요구는 올림(`CEILING`)해 모자라지 않게 한다.
  - 남는 양과 부산물은 `HALF_UP`.
  - 반올림은 `trace`에 `round`로 남는다.
- 개수 단위(ea)의 정수 나눔은 ADR-008처럼 아직 정하지 않는다.

### 9. 정본과 커널

- 정본은 서버(Java)다. 편집기는 서버의 결과를 보인다.
- 편집기에서 즉시 계산이 필요해지면, ADR-040처럼 Java가 고정 입력에 답을 적고 커널이 맞춘다. 이번에는 하지 않는다.

### 10. 검증

- **성질 테스트.** 시드를 고정한 무작위 그래프로 본다. 흐름 커널의 고정 입력 생성기와 같은 방식이다. 1주차는 (a)·(e)로 시작하고, (b)–(d)는 4주차 확정 전에 더한다([로드맵 §12](../../status/ROADMAP-2026-11-23.md) P1).
  - (a) 거꾸로 구한 시작 입력을 앞으로 흘리면 목표 이상이 도착한다(ADR-008 반올림 포함).
  - (b) 목표를 c배 하면 요구도 c배다(반올림 이내).
  - (c) 같은 목표를 다른 단위로 주면 같은 요구다.
  - (d) 손실 0, 분할 없는 직선 그래프에서 요구는 포트 비율의 곱이다.
  - (e) `trace`의 단계를 곱하면 요구가 나온다.
- **도메인 중립.** 데이터 파이프라인 그래프가 공통 층 테스트에 있다(결정 1).
- **통합 테스트.**
  - 메론우유 데모: 재고 부족 하나, 병목 하나
  - 판을 다시 발행한 뒤 확정하면 409이고 아무것도 생기지 않는다
  - 같은 `requestId`는 같은 작업지시를 돌려준다
  - 확정과 계획 조회는 재고를 움직이지 않는다
  - 읽기 권한만 있으면 조회는 되고 확정은 403이다
- **실 API 브라우저 테스트** `melon-milk-journey-real-api.spec.ts`: 로드맵 §8의 합격 기준이다. 처음에는 실패하는 것이 맞다.

### 11. 하지 않는 것

- 고리, 수식 포트, 목표 여럿.
- 가장 싼 계획 고르기(최적화). FM-AI의 일이다.
- 커널 이식, 3D·배치.
- 확정에서 생산 실행 시작. 실행은 지금처럼 작업지시에서 시작한다.

## 결과

- 좋은 점:
  - "목표 → 재료·부족·시간·병목 → 확정"이 한 계산과 한 명령으로 이어진다.
  - 계산 근거가 공통 자산이 된다.
  - 제조 낱말이 공통 층에 들어가지 않는다.
  - 실행 요건 모델이 정해져, 2분기의 자원(에너지·물)과 4분기의 계산 자원(소프트웨어 영역)이 같은 틀을 쓴다.
