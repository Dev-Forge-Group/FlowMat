# ADR-038: 예약·반복 연동 작업(FM-INT-002)

작성일: 2026-11-20

## 상태

**Accepted (2026-11-20).** 사용자가 다음 달 후보 중 FM-INT-002를 앞당겨 하기로 골랐고(2026-11-20), 세부는 2026-10-24 사용자 위임에 따라 권장안이다. 범위는 [월간 계획의 다음 달 후보](../../status/MONTH-PLAN-2026-11-16.md#다음-달-후보-11-20)와 [settingTool 대조표](../../status/SETTINGTOOL-FEATURE-MAP.md) §4-2다. 구현은 아래 "순서"대로 나눠 들어간다.

## 배경

- 지금의 외부 HTTP 연동은 프로젝트별 프로필과 판(허용된 작업 목록), Flow Run 단계의 요청 미리 보기·명시 실행·결과 적용이다([`FlowRunHttpExecutionService`](../../../flowmat_backend/modules/flowrun/src/main/java/org/myweb/flowmat/domain/flowrun/application/FlowRunHttpExecutionService.java)). 사람이 단계를 실행할 때만 돈다. 정해진 때에 반복해 가져오거나 보내는 일은 없다(FM-INT-002).
- 연동 모듈은 다른 모듈에 공개 계약을 준다. 프로필의 작업을 찾는 `ConnectorProfileQuery`(끄기 스위치와 대상 정책을 매번 다시 본다), 한 번 보내는 `ConnectorHttpGateway`(보냈을 수도 있는지 알려 준다), 경계가 있는 JSON 변환 `ConnectorMappingQuery`(`from`·`literal`·`object`, 배열 반복은 없다)다. 자격 증명은 DB가 아니라 서버 설정의 이름으로만 있다.
- 품목·재고 CSV 가져오기가 이미 줄마다 검사하고, 틀린 줄을 빼고 나머지를 한 트랜잭션으로 저장한다([item-import](../../domain/item-import.md) I13, [stock-import](../../domain/stock-import.md) S12). 외부에서 가져오는 자료도 같은 규칙을 지나야 한다.
- settingTool의 외부 적용은 대상을 확인하고, 바뀐 것만 보내고, 다시 읽어 보낸 값과 맞는지 보고, 항목마다 성공·실패·확인 불가를 남긴다. 보내는 쪽은 이 순서를 따른다.

## 결정

1. **새 모듈 `integration`.** `flowmat_backend/modules/integration`. 의존은 platform·project·connector·catalog·inventory이고 모듈 순서에서 inventory 뒤다. 다른 모듈은 공개 계약(`publicapi`)으로만 부른다. 품목·재고 가져오기는 catalog·inventory가 공개 명령(`ItemImportCommand`, `StockImportCommand`)을 새로 내고, 그 안에서 지금의 가져오기 서비스를 그대로 쓴다. 규칙은 하나다.
2. **작업 종류는 셋.**
   - `pull_items`: 프로필의 작업으로 읽고, 응답에서 `rowsAt`(JSON pointer)의 배열을 꺼내 원소마다 `row` 매핑으로 품목 가져오기 줄을 만든다. 품목 가져오기 규칙으로 검사하고, 틀린 줄은 그 줄만 빼고 나머지를 한 트랜잭션으로 저장한다.
   - `pull_stock`: 같은 방식으로 재고 가져오기(기초·입고) 줄을 만든다.
   - `push_stock`: 프로젝트의 품목 코드별 현재 수량을 보낸다. 먼저 `verify` 작업으로 대상의 수량을 읽어 다른 품목만 고르고, `send` 작업으로 그 품목들을 보낸 뒤, 다시 `verify`로 읽어 품목마다 맞음·다름·확인 불가를 남긴다. 보낸 본문은 FlowMat이 만든 문서(`{"items":[{"itemCode","quantity","unit"}]}`)에 작업의 `request` 매핑을 적용한 것이다. **(2026-11-20 구현에서 정한 것)** 작업은 `operationId`(POST·PUT·PATCH로 보냄)와 `verifyOperationId`(GET으로 읽음)를 둘 다 가진다. 매핑의 `row`는 대상의 기록에서 `itemCode`와 `quantity`를 읽고, `request`는 없어도 된다. 견주는 품목은 FlowMat에 재고 행이 있는 품목과 대상이 적은 품목의 합집합이다. FlowMat의 수량은 그 품목의 모든 재고 행(위치·LOT·상태, 예약·격리 포함)의 합이다. 대상이 적었지만 FlowMat에 없는 품목은 `not_in_flowmat`으로 남기고 보내지 않으며 실패로 세지 않는다. 둘 다 0이거나 없으면 보내지 않는다. 다른 품목이 500개를 넘으면 보내지 않고 실패다. 보낸 뒤의 판정은 다시 읽은 대상의 값이 정한다: 답이 성공이고 모두 맞으면 `succeeded`, 하나라도 다르면 `partial`, 대상이 거절하면(HTTP 오류) `failed`, 답을 잃었으면 모두 맞을 때 `succeeded`·아니면 `outcome_unknown`, 다시 읽지 못하면 `outcome_unknown`. 보내지 못했다고 확실하면(연결 전 실패) `failed`다. 처음 읽기에 실패하면 아무것도 보내지 않는다.
3. **매핑.** 행 매핑은 `rowsAt`과 `row`(연동 모듈의 매핑 정의)다. 저장할 때 `ConnectorMappingQuery.validate`로 검사한다. 배열을 도는 일은 작업 쪽이 하고, 매핑 엔진은 고치지 않는다. 한 번에 최대 500줄(가져오기의 한도와 같다).
4. **실행 기록.** 실행마다 `integration_run` 한 줄(시작·끝, 수동·예약, 상태, 수)을 남기고, 항목마다의 결과(줄 번호, 품목 코드, 결과, 사유)는 그 줄의 `items_json`에 함께 둔다. 한 실행이 최대 500항목이고 실행 단위로만 읽으므로 따로 표를 두지 않는다. 작업마다 최근 20회를 보여 준다. 상태는 `succeeded`, `partial`(뺀 줄이나 맞지 않는 품목이 있음), `failed`, `outcome_unknown`(보냈을 수도 있으나 확인하지 못함)이다. 요청·응답 본문은 남기지 않는다(연동 모듈의 원칙: 응답 JSON은 일시적이다). 미리 보기는 읽기와 가져오기 검사(dry run)만 하고 아무것도 저장하지 않으며 기록도 남기지 않는다.
5. **보내기와 트랜잭션.** Flow Run의 HTTP 실행과 같다. 실행을 트랜잭션 안에서 잡고(claim), 트랜잭션을 닫은 뒤 보내고, 결과를 새 트랜잭션에 적는다. 보냈을 수도 있는데 답을 못 받으면 `outcome_unknown`이고, 다음 실행의 첫 `verify`가 대상의 실제 값을 읽으므로 같은 품목을 두 번 늘리지 않는다(보내는 값은 증감이 아니라 수량 그대로다). 한 작업의 실행은 한 번에 하나다(`status = 'running'` 부분 유일 색인). 10분이 지나도 `running`인 실행은 서버가 멈춘 것으로 보고, 다음에 그 작업을 잡을 때 `outcome_unknown`("끝나지 않았다; 읽은 것이 저장됐는지 모른다")으로 닫는다. 읽기는 15초 안에 끝나므로 10분은 넉넉하다.
6. **예약.** 작업마다 선택 `schedule_cron`(분 단위 5칸)을 두고 프로젝트 업무 시간대([project-time-zone](../../domain/project-time-zone.md))로 해석한다. 간격은 15분보다 짧을 수 없다. 다음 시각 `next_run_at`을 저장한다. 서버마다 1분에 한 번 기한이 된 작업을 `FOR UPDATE SKIP LOCKED`로 가져가 `next_run_at`을 다음 시각으로 옮기고, 실행 줄을 `(job_id, scheduled_for)` 유일 키로 넣는다. 서버가 여럿이어도 같은 회차는 한 번만 돈다. 서버가 멈춰 있던 동안 지난 회차는 따라잡지 않고 다음 시각부터 간다. 앞 실행이 아직 도는 중이면 그 회차는 건너뛴다(쌓아 두지 않는다). 이미 돈 회차가 다시 기한이 되면(느린 시계의 서버가 같은 시각을 다시 적은 경우) 돌리지 않는다. **예약은 `pull_items`(와 3단계의 `push_stock`)만 한다(2026-11-20 구현 중 정함).** 재고 가져오기는 읽은 수량을 입고하므로 같은 목록을 다시 읽으면 또 입고한다. 가져오기가 이미 받은 입고를 알아볼 수 있을 때(원천의 참조 번호)까지 `pull_stock`은 손으로만 돌린다. 품목은 같은 기록이 다시 와도 "바뀐 것 없음"이라 반복해도 된다. API는 `PUT /projects/{projectId}/integration-jobs/{jobId}/schedule`(`cron`, `enabled`, `version`)이다.
7. **누구의 권한으로.** 작업을 만들고 고치는 것은 프로젝트 소유자다(연동 프로필과 같다). 예약을 켠 사람이 `run_as`가 되고, 실행마다 그 사람이 아직 프로젝트에 쓸 수 있는지 다시 본다. 실행은 그 사람의 이름으로 기록된다(가져오기의 만든 사람, 원장의 행위자). 권한을 잃었으면 그 실행은 `failed`다. 예약 실행은 그 사람을 현재 사용자로 둔 채(`ActingUser`) 화면의 요청과 같은 검사를 지난다. 그 사람이 가진 것보다 더 하지 않는다.
8. **멈춤.** 예약 실행이 연이어 3번 `failed`면 작업의 예약을 끄고 사유를 남긴다("Switched off after 3 failed runs in a row. The last: …"). 사람이 고쳐서 다시 켜면 세기가 0부터 다시 간다. 수동 실행은 세지 않고, `failed`가 아닌 예약 실행은 세기를 0으로 돌린다.
9. **하지 않는 것.** 범용 iPaaS, 사용자가 쓰는 스크립트, 받는 쪽 웹훅, 품목·재고 밖의 대상(주문 등), 한 실행 안의 재시도(다음 예약이 재시도다), 지난 회차 따라잡기.

## 순서

1. 모듈, 표(V137), 작업 저장(소유자), 수동 실행과 미리 보기(`pull_items`, `pull_stock`), 실행 기록.
2. 예약: 저장, 다음 시각 계산, 잡기(잠금과 유일 키), `run_as`, 연속 실패 멈춤.
3. `push_stock`: 읽기 → 다른 것만 보내기 → 다시 읽어 검증.
4. 화면: 프로젝트 설정의 연동 작업 목록·양식·미리 보기·지금 실행·예약·실행 기록.

## 결과

- 좋은 점: 외부 자료가 화면의 가져오기와 같은 규칙으로 들어온다. 보내는 쪽은 settingTool처럼 결과를 항목마다 확인한다. 서버가 여럿이어도 회차가 겹치지 않는다.
- 비용: 모듈 하나, 표 둘(`integration_job`, `integration_run`), 공개 명령 둘, 예약 감시 하나가 는다. 매핑을 JSON으로 적어야 하므로 화면의 미리 보기가 중요하다.

## 검증

- 통합 테스트는 실제 Postgres와 가짜 `ConnectorHttpGateway`로 한다. 품목·재고 가져오기(틀린 줄은 빠지고 나머지는 저장, 기록), 미리 보기는 아무것도 바꾸지 않음, 소유자가 아니면 403, 예약 잡기를 두 번 동시에 해도 한 번만 실행, 권한을 잃은 `run_as`, 연속 실패 멈춤, 밀기에서 다른 품목만 보내고 다시 읽어 맞음·다름·확인 불가를 남김, 보냈는지 모르는 실행.
- 브라우저 테스트(가짜 API): 작업 만들기, 미리 보기, 지금 실행, 예약 켜기·끄기, 실행 기록.
