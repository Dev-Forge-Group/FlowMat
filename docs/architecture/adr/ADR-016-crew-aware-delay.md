# ADR-016: 인력 근무에도 맞춘 연결 지연

작성일: 2026-10-18

## 상태

**Accepted (2026-10-18). 로컬 구현 2eu(2026-10-18, 커밋 전, 마이그레이션 없음).** 사용자 지시("어떤기능이던 지금 구현된 기능과 연관된것 부터 처리해", 2026-10-18)에 따라 [ADR-015](ADR-015-shift-aware-delay.md) "결정하지 않은 것"의 첫 항목을 골랐다. 세부는 같은 날 사용자 사전 위임("구현 중 새 설계 선택 | 권장안으로 진행")에 따라 리드가 고른 권장안이다.

근거: [ADR-015](ADR-015-shift-aware-delay.md), [작업자 달력](../../domain/worker-calendar.md) WC17·WC24·WC36·WC39, [ADR-013](ADR-013-rota-history.md)(근무표 판).

## 배경

| # | 지금 | 근거 |
|---|---|---|
| P1 | 생산 단계는 연결 지연이 작업지시 설비의 근무 밖에 끝나면 다음 가용 시간으로 미룬다. 인력은 보지 않는다 | ADR-015 |
| P2 | 작업지시에는 인력(crew)과 사람마다 몫이 있다 | WC13, WC36 |
| P3 | 계획 제안은 설비 가용 시간 ∩ 몫 100%이고 교대가 있는 인력 모두의 근무 시간에만 생산 시간을 센다 | WC24, WC39 |
| P4 | 그래서 계획은 사람이 일할 때로 잡히는데, 실행 중 지연 뒤 단계는 사람이 없는 시각으로 잡힐 수 있다 | |
| P5 | 작업자 근무 시간(판, 날짜별 교대, 쉬는 날, 휴일)은 workforce 공개 API `WorkerCalendarQuery.workingTime`이 준다. production이 이미 쓴다 | WC17 |

## 결정

| # | 결정 | 누가 |
|---|---|---|
| 1 | 지연이 끝난 시각(`readyAt`)부터, 설비가 가용하고(ADR-015 결정 2·4 그대로) **몫 100%이고 교대가 있는 인력이 모두 일하는** 첫 시각으로 미룬다. 계획 제안(WC24·WC39)과 같은 사람을 본다 | 사용자 사전 위임(2026-10-18) |
| 2 | 작업지시에 설비가 없어도 그런 인력이 있으면 인력만으로 미룬다. ADR-015 결정 1의 "설비가 없으면 그대로"는 그런 인력도 없을 때로 좁힌다 | 사용자 사전 위임(2026-10-18) |
| 3 | 몫이 100% 미만인 사람과 교대가 없는 사람은 시각을 정하지 않는다(WC39, WC17 `calendarSet = false`) | 사용자 사전 위임(2026-10-18) |
| 4 | 1년 안에 함께 일하는 시각이 없거나 설비가 지워졌으면 `readyAt` 그대로 둔다(ADR-015 결정 4와 같음) | 사용자 사전 위임(2026-10-18) |
| 5 | 기록: 미뤘으면 `step_scheduled`에 `crew`(시각을 정한 사람들 ID)를 더한다. 설비가 없으면 `equipmentId`는 없다. 화면 지연 줄은 설비만이면 지금 그대로, 인력만이면 `, then the crew's next working time`, 둘 다면 `, then the next time the equipment and crew work` | 사용자 사전 위임(2026-10-18) |
| 6 | 바로 시작(ADR-015 결정 6): 지연이 끝났고 지금 설비와 그 인력이 모두 일하면 시작할 수 있다. 사람의 야근은 그날의 날짜별 교대(WC29)로 둔다 | 사용자 사전 위임(2026-10-18) |
| 7 | 의존: production의 `ProductionRunWorkingTime`이 workforce 공개 API를 더 쓴다. flowrun 공개 API의 `WorkingStart`에 `crew`를 더한다. 새 마이그레이션은 없다 | 사용자 사전 위임(2026-10-18) |

## 예

- 프레스는 달력이 없어 항상 가동. 인력 kim(몫 100%)은 08:00–17:00 월–금. Mix가 금요일 16:00에 끝나고 지연 2시간 → `readyAt` 금 18:00 → Bake `scheduledAt` 월 08:00. 이벤트에 `crew` [kim]과 `equipmentId` 프레스.
- 같은 작업지시에 lee(몫 50%)도 있으면 lee의 근무는 보지 않는다.
- 설비 없는 작업지시에 kim만 있어도 kim의 근무로 미룬다.
- 금요일 19:00에 kim의 날짜별 교대(야근)를 두면 Bake를 바로 시작할 수 있다.

## 수용 기준 (2026-10-18)

- [x] 보는 인력: **몫 100%이고 교대가 있는 사람**(WC39와 같음)
- [x] 설비가 없을 때: **인력만으로 미룸**
- [x] 기록, 화면, 바로 시작: 결정 5·6
- [x] 새 마이그레이션: **없음**

## 결정하지 않은 것

- ~~몫 100% 미만인 사람을 비율로 반영할지~~ → [ADR-023](ADR-023-labor-step-followups.md) 결정 9–10(2026-10-30): 계획 제안의 노동은 몫만큼 세고, 지연은 그대로
- 실제로 일한 사람(실적)과 견주는 것. [ADR-019](ADR-019-run-labor.md)에서 정했다(2026-10-19)

## 결과

- 좋은 점
  - 계획 제안과 실행 중 지연이 같은 사람 기준으로 잡힌다.
- 위험
  - 단계가 생길 때 사람 근무 시간 계산이 더해진다. 앞 1주, 1달, 1년 순으로 좁게 먼저 찾는다.
  - 인력만 있는 작업지시는 이제 지연 뒤 단계가 늦어질 수 있다. 그날 교대를 두면 바로 시작할 수 있다(결정 6).

## 구현 메모 (2026-10-18, 2eu)

- production의 `ProductionRunWorkingTime`이 작업지시의 설비와 인력(`work_order_crew`, 몫 100%)을 읽는다. 인력 근무 시간은 `WorkerCalendarQuery.workingTime`, 설비는 `EquipmentWorkingTimeQuery.workingStretches`다.
- 함께 일하는 첫 시각: 창마다 설비의 시작 가능 구간을 한 번 구하고, 사람마다 근무 구간과 교차해 그 첫 시각을 쓴다(계획 제안 WC24와 같은 방식). 앞 7일, 31일, 366일 순으로 찾는다. 2026-10-18 정정(오류 담당 보고): 처음 구현은 설비와 사람을 번갈아 옮기는 탐색을 200바퀴에서 멈춰, 엇갈리는 날이 이어지다 300일 뒤에야 함께 일하는 경우 `readyAt`으로 돌아갔다. 엇갈리는 1년을 끝까지 훑는 최악은 12초였다. 지금은 창마다 설비의 시작 가능 구간을 한 번 구하고 사람마다 근무 구간과 교차해 첫 시각을 쓴다(최악 0.2초).
- 이벤트 `crew`는 시각을 정한 사람(몫 100%이고 교대가 있는 사람)이다. 화면 문구는 `heldText`(`pages/runs/model/delayText.ts`)가 정한다.
- 2ew(2026-10-18): 생산 단계 응답에도 `held {readyAt, equipmentId, equipmentCode, crew[]}`를 둔다. 실행 화면 Process steps에서 기다리는 설비와 사람이 보인다(`· from … (waits for PRESS, kim)`). 결정 5의 기록을 화면까지 잇는 것이라 새 결정은 아니다.
- 검증은 [Flow Run](../../domain/flow-run.md) F14와 그 검증 문단.
