# ADR-007: 합류(Join) 게이트웨이

작성일: 2026-10-17

## 상태

**Accepted (2026-10-17, 사용자 결정 "Accept as recommended"). 로컬 구현 2ef(2026-10-17, V88, 2026-10-18 `9500678`에서 커밋).** 같은 날 사용자 요청("Join decision draft")으로 Proposed 초안을 썼고, 사용자가 권장안 그대로 수용 기준 8개를 닫았다. [ADR-006](ADR-006-operation-types.md) 결정 9가 별도 결정으로 넘긴 기준(기다릴 갈래, 중첩 분기, 건너뛰거나 실패한 갈래, 재시도 중복 도착, 합친 입력 모양)을 아래 결정으로 정한다. 승인과 구현은 별개다.

근거: [ADR-006](ADR-006-operation-types.md)(게이트웨이 노드, Exclusive 구현 2eb), [연결 계약](../../domain/process-port-connection-contract.md) GR-01–GR-20, [노드 실행 정책](../../domain/flow-run-execution-policy.md)(재시도·시간 제한), [벤치마크](../../reference/benchmarks/FlowMat_GitHub_Benchmark_2026-09-24.md) FM-PLAN-001(JOIN). 참고한 개념은 Conductor의 JOIN, BPMN의 병렬 합류·포함 합류다. 코드는 가져오지 않는다.

## 배경 (2026-10-17 코드 기준)

지금 그래프 실행에서 합류와 얽히는 동작은 아래와 같다.

| # | 지금 동작 | 근거 |
|---|---|---|
| B1 | 출발 단계가 완료되면 통과한 연결마다 대상 단계를 **따로** 만든다. 두 갈래가 한 노드로 모이면 그 노드의 단계가 둘 생긴다 | GR-04, `FlowRunGraphIntegrationTest.convergingPathsRetainTheExactUpstreamStep` |
| B2 | 순환 그래프는 실행하지 않는다. 그래서 한 실행에서 한 연결로 도착하는 횟수는 그 연결 출발 노드의 단계 수만큼이다. 출발 노드의 단계가 여럿이 되는 것은 위쪽에서 갈래가 다시 모일 때뿐이다 | GR-01 |
| B3 | 재시도는 같은 단계의 새 시도다(즉시, 또는 `retryAt`까지 planned로 대기). 단계는 한 번만 완료되므로 **재시도만으로 같은 연결이 두 번 도착하지 않는다** | GR-05, [실행 정책](../../domain/flow-run-execution-policy.md) EP4–EP6 |
| B4 | 건너뛴 단계(`skip` 정책)는 다음으로 가지 않는다. 다음 연결로 가는 것은 완료뿐이다. 조건이 거짓인 연결과 Exclusive가 고르지 않은 연결도 단계를 만들지 않는다(`connection_filtered`) | GR-05, GR-11, GR-16 |
| B5 | `stop` 정책의 실패와 Exclusive의 `NO_ROUTE`는 실행 전체를 실패시킨다 | GR-05, GR-15 |
| B6 | 단계의 출처는 하나다(`source_step_id`, V40). 계보 API는 그 사슬을 따라간다 | V40, `GET …/steps/{stepId}/lineage` |
| B7 | 단계 상태를 바꾸는 모든 요청(시작·완료·실패·건너뜀·시간 초과 감시)은 실행 행을 잠그고 차례로 처리한다 | `FlowRunStepService` |
| B8 | 서버가 바로 완료하는 단계는 Exclusive 게이트웨이뿐이다 | ADR-006 결정 4, GR-17 |

ADR-006이 걱정한 "먼저 도착한 갈래가 합류를 일찍 끝내는" 문제는, 합류가 "지금까지 온 것"만 보고 닫힐 때 생긴다. 아직 살아 있는(계획·진행·재시도 대기) 단계가 그 합류에 닿을 수 있는데도 닫히는 경우다.

## 선택지: 언제 합류하는가

| 안 | 내용 | 좋은 점 | 약점 |
|---|---|---|---|
| A. 모든 진입 연결(정적 AND) | 진입 연결마다 한 번 이상 도착해야 합류한다. 끊긴 갈래(조건 거짓·Exclusive 미선택·건너뜀)는 "오지 않음" 표시를 아래로 전파해 기다림을 푼다 | BPMN 병렬 합류와 같아 익숙하다 | 끊긴 갈래 표시를 그래프 따라 전파하는 기록이 따로 필요하다. 같은 연결로 두 번 도착하면(B1·B2) 어느 것을 쓸지 또 정해야 한다 |
| B. 더 올 수 있는 갈래가 없을 때(도달 가능성) | 진입 연결마다 "도착했거나, 이 실행에서 더는 올 수 없을 때" 한 번 합류한다. "올 수 있음"은 살아 있는 단계(planned·running, 재시도 대기 포함)에서 고정된 revision 그래프를 따라 그 연결에 닿을 수 있다는 뜻이다 | 조건·Exclusive·건너뜀·중첩 분기·수렴 경로를 한 규칙으로 다룬다. 살아 있는 단계가 닿을 수 있으면 닫히지 않으므로 일찍 끝나지 않는다. 그래프에 순환이 없어(B2) 계산이 반드시 끝난다 | 합류 시점이 실행 전체 상태에 달려 있어, 단계 상태가 바뀔 때마다 다시 계산해야 한다 |
| C. 첫 도착 | 처음 온 갈래로 바로 진행하고 나머지는 기록만 한다 | 가장 단순하다 | 나머지 갈래의 결과가 버려진다. 기본 방식으로는 맞지 않다 |
| D. N개 중 M개 | 정해진 수가 오면 진행한다 | 투표·여유분 공정에 맞다 | 나머지를 어떻게 처리할지 또 정해야 한다. 후속 선택지로 남긴다 |

## 결정 (2026-10-17, 권장안 그대로)

1. **B(도달 가능성).** Join은 ADR-006의 게이트웨이 노드 종류로 더한다(노드 종류 `join`). 실행마다 한 번만 합류한다.
2. **기다림의 끝:** 진입 연결마다 (가) 도착했거나 (나) 살아 있는 어떤 단계에서도 그 연결에 닿을 수 없으면 합류한다. 살아 있는 단계는 planned·running이다(재시도 대기·예정 시각 대기, 기다리는 다른 Join 포함). 완료·건너뜀·실패·취소된 단계는 더 라우팅하지 않으므로 살아 있지 않다.
3. **다시 보는 때:** 실행의 단계 상태를 바꾸는 모든 곳(완료, 실패와 그 정책, 건너뜀, 시간 초과 감시, Exclusive 통과)에서 기다리는 Join을 다시 본다. 같은 실행 행 잠금 안에서 하므로(B7) 두 갈래가 동시에 끝나도 한 번만 합류한다.
4. **일부만 도착:** 끊긴 갈래(조건 거짓, Exclusive 미선택, 건너뜀)를 뺀 나머지가 모두 도착하면 진행한다. **하나도 도착하지 않으면** Join 단계를 만들지 않고 그 뒤도 진행하지 않는다. 실행은 마칠 수 있다.
5. **같은 연결로 여러 번 도착**(위쪽 수렴, B1·B2): 모두 모아 한 번 합류한다. 재시도는 도착을 늘리지 않는다(B3).
6. **Join 단계의 모양:** 첫 도착 때 planned로 만들고, 도착마다 `join_arrived` 이벤트(연결·출처 단계)를 남긴다. 사람이 시작·완료할 단계가 아니다. 합류하면 서버가 system으로 완료한다(ADR-006 결정 4의 예외를 Join에도 넓힌다). 재고·생산 기록은 움직이지 않는다.
7. **합친 입력과 출력:** `arrivals[{connectionId, sourceStepId, quantity, unit, item, attrs}]`(도착 순서)로 담는다. 모든 도착에 `quantity`가 있고 `unit`이 같으면 위쪽에 `quantity`(합)와 `unit`을 둔다. `item`이 모두 같으면 `item`도 둔다. `attrs`는 합치지 않고 도착마다 그대로 둔다. 출력은 입력과 같고, 나가는 연결의 조건·용량·포트 규칙(GR-02·GR-03·GR-07·GR-08)은 이 출력으로 본다.
8. **출처 기록:** 단계의 출처가 하나라는 지금 모델(B6)로는 Join을 나타낼 수 없다. 새 표(단계·출처 단계·연결·도착 시각)에 모든 출처를 두고, 계보 API의 조상은 여러 부모를 따라 단계 순번 순으로 돌려준다. 새 마이그레이션이 필요하다.
9. **합친 출력이 다음 연결 규칙을 통과하지 못할 때:** 계기가 완료 보고면 그 보고를 409로 거절해 다시 보낼 수 있게 한다(GR-18과 같음). 계기가 건너뜀·시간 초과처럼 사람이 다시 보낼 수 없는 일이면 Join 단계를 `JOIN_TRANSFER_REJECTED`로 실패시키고 실행도 실패한다.
10. **발행 검사:** 오류 `JOIN_WITHOUT_INPUT`(진입 연결 없음), 경고 `JOIN_SINGLE_INPUT`(진입 연결 하나). 기본 연결 표시는 지금처럼 Exclusive에서 나가는 연결에만 둔다(GR-19). 이전 revision은 그대로 돈다.
11. **화면:** 팔레트에 **Join**. 실행 화면의 Join 단계에 "기다리는 갈래 N개 / 도착 M개"를 보이고, 계보에 여러 출처를 보인다.

## 예

- 병렬 두 갈래: A → (B, C) → J. B가 완료되면 도착 1이고 C가 살아 있어 기다린다. C가 완료되면 합류한다.
- Exclusive 뒤: A → X(Exclusive) → (B, C) → J. X가 B만 고르면 C 갈래는 끊긴다. B가 완료되면 더 올 갈래가 없으므로 도착 1로 합류한다.
- 건너뜀: A → (B, C) → J에서 C가 skip되면 B 완료로 합류한다. B가 먼저 끝났는데 C가 재시도 대기 중이면 C가 살아 있으므로 기다린다.
- 중첩: A → (B, C), B → (B1, B2) → J1 → J2, C → J2. J1은 B1·B2를, J2는 J1과 C를 기다린다. 분기와 합류의 짝을 맞추는 규칙 없이 도달 가능성만으로 된다.
- 수렴: A → (B, C) → D → J, E → J. D의 단계가 둘(B에서, C에서) 생겨 D → J로 두 번 도착한다. 둘 다 모아 E와 함께 한 번 합류한다.

## 결정하지 않은 것

- 수량 분할(SPLIT)과 갈래별 수량 배분
- N개 중 M개 합류(안 D), 시간 제한이 있는 합류(정한 시간이 지나면 도착한 것만으로 진행)
- 하위 흐름(SUBFLOW), 루프(순환 그래프는 계속 거절)
- 수동 실행(manual 모드)과 생산 실행에 연결된 실행에서의 합류

## 결과

- 좋은 점
  - 조건·Exclusive·건너뜀이 섞여도 Join이 일찍 닫히거나 끝없이 기다리지 않는다.
  - 기존 그래프와 이전 revision의 동작은 그대로다. Join 노드가 없으면 GR-04 그대로 돈다.
- 위험
  - 단계 상태가 바뀔 때마다 기다리는 Join의 도달 가능성을 다시 계산한다. 그래프가 작고 순환이 없어 비용은 작다. 다만 시간 초과 감시를 포함해 모든 상태 변경 경로에 빠짐없이 넣어야 한다.
  - 계보 API의 조상이 사슬에서 여러 부모로 바뀌므로 화면과 API 사용처를 함께 고쳐야 한다.
  - 서버가 스스로 완료하는 단계가 Exclusive 말고도 생긴다.
