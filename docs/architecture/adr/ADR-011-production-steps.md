# ADR-011: 생산 실행의 공정 단계와 노드별 지침

작성일: 2026-10-17

## 상태

**Accepted (2026-10-17, 사용자 결정 "Accept as recommended"). 로컬 구현 2el(2026-10-17, V91, 2026-10-18 `9500678`에서 커밋).** 같은 날 사용자 요청("Production steps ADR")으로 초안을 썼고, 사용자가 권장안 그대로 수용 기준 8개를 닫았다.

근거: [실행 모델](../execution-model.md) §5·§6·§8, [Flow Run](../../domain/flow-run.md), [연결 계약](../../domain/process-port-connection-contract.md) GR-01–GR-52, [작업 지침](../../domain/work-instruction.md), [검사 기준](../../domain/inspection-standard.md), [ADR-002](ADR-002-module-dependency.md)(모듈 경계), [ADR-003](ADR-003-resource-port-contract.md).

## 배경

| # | 지금 | 근거 |
|---|---|---|
| P1 | 생산 실행은 작업지시, BOM, 발행 revision을 시작할 때 고정하고 투입·산출을 기록한다. 재고 거래와 LOT 계보는 그 기록에서 생긴다. 실행은 한 번 시작해서 한 번 마감한다 | 실행 모델 §6·§8 |
| P2 | 발행 revision이 있는 생산 실행은 연결된 Flow Run을 하나 만든다. 이 Flow Run은 시작과 마감만 기록한다. 실행 방식은 기본값 `manual`이고 단계가 없다 | `LinkedFlowRunService` |
| P3 | Flow Run 단계 API는 생산에 연결된 실행을 409로 거절한다: `Production-linked steps must be recorded through the production run API.` 그런데 생산 쪽에는 그 API가 없다 | `FlowRunStepService` |
| P4 | 투입·산출 행(`production_run_item`)은 이미 노드(`processId`, `processIoId`)를 가질 수 있고, 실행 revision의 스냅샷으로 검사한다. 노드별로 무엇이 들어가고 나왔는지는 남지만, 그 노드가 언제 시작하고 끝났는지는 없다 | `ProductionRunServiceImpl` |
| P5 | 작업 지침은 제품마다 revision이 하나이고, 체크리스트는 실행 하나에 붙는다. 지침 단계가 어느 공정의 것인지는 적을 곳이 없다. 지침이 마감을 막게 할 수 있다(F1) | [작업 지침](../../domain/work-instruction.md) |
| P6 | 검사 기준은 제품별이고, 지침 단계가 기준을 따르면 확인할 때 검사가 함께 남는다(W13, R9) | [검사 기준](../../domain/inspection-standard.md) |
| P7 | 그래프 실행은 노드마다 단계를 만들고, 외부가 단계를 시작·완료한다. 조건, 용량, 포트 규칙, 게이트웨이, 손실, 지연, 실행 정책이 모두 여기서 돈다 | GR-01–GR-52, [노드 실행 정책](../../domain/flow-run-execution-policy.md) |

그래서 실제 생산에서는 그림의 공정 순서가 실행에 쓰이지 않는다. 노드마다 다른 작업 지침을 둘 수도 없다. 그래프 실행에 만든 규칙(분기, 합류, 분할, 손실, 지연)도 생산 실행에서는 쓰이지 않는다.

## 선택지

### 1. 공정 단계를 어디에 둘까

| 안 | 내용 | 좋은 점 | 약점 |
|---|---|---|---|
| A. 연결 Flow Run을 그래프로 | 생산 실행이 시작될 때 연결 Flow Run을 그래프 방식으로 만들고 뿌리 노드 단계를 놓는다. 작업자는 생산 실행 화면에서 단계를 시작·완료한다 | 그래프 실행의 규칙과 기록을 그대로 쓴다. P3에서 비워 둔 자리와 맞는다 | 생산 쪽에 단계 API가 생기고, 두 모듈이 함께 바뀐다 |
| B. 생산 쪽에 새 표 | `production_run_step` 같은 표를 따로 둔다 | production 안에서 끝난다 | 그래프 실행과 같은 규칙을 한 번 더 만든다 |
| C. 단계 없이 지침만 노드로 묶기 | 지침 단계에 노드를 적어 체크리스트를 노드별로 보이기만 한다 | 가장 작다 | 공정 순서와 그래프 규칙은 여전히 쓰이지 않는다 |

### 2. 단계를 완료할 때의 출력

| 안 | 내용 |
|---|---|
| a. 기록에서 채움 | 보고에 출력이 없으면 그 노드에 기록된 산출의 합으로 채운다. 보고가 직접 보낼 수도 있다 |
| b. 매번 보고 | 작업자가 수량을 직접 적는다 |
| c. 출력 없음 | 단계 출력은 비워 둔다. 조건·분할·손실은 쓸 수 없다 |

### 3. 마감과 열린 단계

| 안 | 내용 |
|---|---|
| a. 진행 중이면 막음 | 진행 중 단계가 있으면 마감은 409. 아직 시작하지 않은 단계는 마감할 때 취소한다 |
| b. 모두 끝나야 마감 | 모든 단계가 완료되거나 건너뛰어져야 마감할 수 있다 |
| c. 상관없음 | 마감은 단계와 무관하다. 열린 단계는 그대로 남는다 |

## 결정 (2026-10-17, 권장안 그대로)

1. **A.** 이 결정 뒤에 시작하는 생산 실행부터, revision이 있으면 연결 Flow Run을 그래프 방식으로 만들고 뿌리 노드 단계를 놓는다. 이미 진행 중인 실행은 지금처럼 단계 없이 둔다.
2. **API는 생산 실행 쪽에 둔다.** `GET /production-runs/{id}/steps`, `POST /production-runs/{id}/steps/{stepId}/start`, `…/complete`, `…/fail`. production은 flowrun 공개 API로만 부른다(ADR-002). Flow Run 단계 API는 지금처럼 연결 실행을 거절한다.
3. **출력은 a.** 보고에 출력이 없으면, 그 노드에 기록된(취소되지 않은) 산출이 한 품목·한 단위일 때 `{quantity, unit, item}`으로 채운다. 그렇지 않으면 빈 출력이다. 보고가 보낸 출력이 있으면 그것을 쓴다.
4. **재고는 단계가 움직이지 않는다.** 재고 거래와 LOT 계보는 지금처럼 투입·산출 기록에서만 생긴다(실행 모델 §8). 시뮬레이션·시험 실행도 단계는 똑같이 돌고 재고만 움직이지 않는다(§7).
5. **게이트웨이와 연결 규칙은 그래프 실행과 같다.** Exclusive, Join, Split은 서버가 지나가고, 용량, 포트 규칙, 손실, 지연(GR-01–GR-52)이 단계 출력에 적용된다.
6. **노드별 지침:** 지침 단계에 노드(`process_id`)를 적을 수 있게 한다(새 마이그레이션). 노드가 적힌 단계는 그 노드의 단계에서 보이고, 적히지 않은 단계는 지금처럼 실행 전체의 것이다. 실행 revision에 없는 노드가 적힌 단계는 "그 밖"으로 보인다.
7. **노드를 완료할 때:** 지침이 마감을 막게 되어 있으면(F1) 그 노드의 필수 지침 단계를 모두 확인해야 완료할 수 있다. 막지 않게 되어 있으면 완료는 되고, 응답에 확인하지 않은 단계 수가 나온다.
8. **마감은 a.** 진행 중 단계가 있으면 409. 시작하지 않은 단계는 마감할 때 취소하고(`step_cancelled`, 이유 `run_finished`), 연결 Flow Run은 지금처럼 끝낸다.
9. **화면:** 생산 실행 상세에 **Steps**를 둔다. 노드마다 상태, 시작·완료 버튼, 그 노드의 지침 단계, 그 노드에 기록된 투입·산출이 보인다.

## 예

- 혼합 → 성형 → 굽기 실행: 시작하면 혼합 단계가 생긴다. 혼합을 완료하면 성형 단계가 생기고, 혼합에 기록한 산출 100 kg이 출력이 된다.
- 굽기 지침에 "오븐 온도 확인"(필수)이 노드 굽기로 적혀 있고 지침이 마감을 막으면, 그 확인 전에 굽기를 완료하면 409다.
- 성형이 진행 중일 때 실행을 마감하면 409다. 성형을 완료하고 굽기가 아직 시작 전이면, 마감할 때 굽기 단계가 취소된다.

## 수용 기준 (2026-10-17 사용자 확정)

- [x] 단계를 둘 곳: **A 연결 Flow Run을 그래프로**
- [x] 적용 범위: **결정 뒤 시작하는 실행부터**
- [x] API: **생산 실행 쪽에 두고 flowrun 공개 API로 부름**
- [x] 출력: **a 기록된 산출로 채움, 보고가 덮을 수 있음**
- [x] 재고: **단계는 재고를 움직이지 않음**
- [x] 노드별 지침: **지침 단계에 노드를 적음(새 마이그레이션)**
- [x] 노드 완료와 지침: **마감을 막는 지침일 때만 필수 단계가 완료를 막음**
- [x] 마감: **a 진행 중이면 409, 시작 전 단계는 취소**

## 결정하지 않은 것

- 검사 기준을 노드에 직접 두는 것. 지금은 지침 단계를 통해서만 노드와 이어진다.
- 노드마다 설비나 인력을 정하는 것, 노드별 가동 시간 기록
- 작업지시 계획을 노드(공정)별로 나누는 것
- 단계를 자동으로 시작하는 실행기

## 결과

- 좋은 점
  - 그림의 공정 순서와 그래프 규칙이 실제 생산 실행에서도 쓰인다.
  - 노드마다 작업 지침을 따로 확인할 수 있다.
  - 기존 진행 중 실행과 재고 규칙은 바뀌지 않는다.
- 위험
  - production과 flowrun이 함께 바뀐다. 공개 API를 넓혀야 한다.
  - 생산 실행 화면이 커진다. 단계, 투입·산출, 지침이 한 화면에 모인다.
  - 출력 자동 채움(결정 3)이 품목이 여럿인 노드에서는 빈 출력이 되어, 그런 노드의 조건·분할은 작업자 보고에 기댄다.
