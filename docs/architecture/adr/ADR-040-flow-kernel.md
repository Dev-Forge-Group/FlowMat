# ADR-040: 흐름 커널(flow kernel)

작성일: 2026-11-21

## 상태

**Accepted (2026-11-21).** [월간 계획 11-23 ~ 12-18](../../status/MONTH-PLAN-2026-11-23.md)의 첫 결정이다. 사용자 지시(11-21)는 "서비스의 본질에 집중하고, 스펙·빌드·언어는 바꿔도 된다"이고, 세부는 2026-10-24 위임에 따라 권장안이다. 서버가 커널을 쓸지(결정 6)는 4주차의 측정으로 정한다. 2026-11-21: 결정 5의 고정 입력이 생겼고, Rust 검증과 경로 계산이 모든 고정 입력에서 Java와 같은 답을 낸다(#130). 편집기 연결(결정 7)은 아직이다.

## 배경

- 흐름의 의미는 지금 서버 Java 세 곳에 있다.
  - `WorkflowValidationService`(654줄): 검증 31규칙(이슈 코드 31개). 근거(`evidence`), 고치는 법(`supportedFixes`), 숨기는 경고(`suppresses`)를 함께 낸다.
  - `ProcessConnectionServiceImpl.validateConnectionContract`: 연결 하나의 계약. 포트 방향, 같은 품목, 스키마 호환을 본다.
  - `FlowRunGraph`(400줄): 발행된 판을 실행할 때의 경로 결정이다. 배타 게이트웨이, 수량 분할, 합류, 손실률·지연을 다룬다.
  - 여기에 조건식 언어 `ConditionExpression`과 포트 스키마 `PortSchema`가 쓰인다.
- 편집기에는 조건식만 Rust→WebAssembly로 같은 답을 낸다([compute](../../../compute/condition-expression/README.md), 11-20).
  - 그 밖의 검증은 저장된 그래프를 서버에 물어야 보인다(`useWorkflowValidationQuery`).
  - 흐름을 "돌려 보려면" 발행하고 실행(`simulation` 종류)을 만들어야 한다.
- 검증이 쓰는 바깥 정보는 둘뿐이다. 알려진 단위 코드(`CatalogQuery.isKnownUnitCode`)와 표준 자원 종류(`ResourceTypes`, 고정 목록)다. 나머지는 모두 그래프 안의 값이다.

## 결정

1. **크레이트 하나: `compute/flow-kernel`.**
   - 조건식 언어 크레이트를 흡수한다. 조건식은 모듈 하나가 되고, 고정 입력 1,641개는 그대로 지킨다.
   - Rust 1.97.0, 의존성은 `serde_json`뿐이다. 빌드는 조건식과 같이 재현 가능한 WASM이다(`wasm/build.sh --check`).
2. **범위.**
   - 포트 스키마와 포트 호환(연결 계약).
   - 조건식.
   - 검증 31규칙과 그 근거·고치는 법·숨기는 경고.
   - 경로 계산: 배타 게이트웨이(조건·우선순위·기본 경로), 수량 분할(비율·나머지), 합류(기다리는 입력), 손실률, 지연.
   - 시간·용량·달력은 넣지 않는다. 그것은 다음 달 후보다.
3. **입력은 그래프 하나의 JSON.**
   - `{processes, ports, connections, context: {knownUnits}}`로 넣는다. 각 항목은 서버 DTO와 같은 필드 이름을 쓴다. 편집기는 이미 가진 캔버스 상태로, 서버는 저장소에서 읽은 값으로 같은 JSON을 만든다.
   - 표준 자원 종류는 커널에 고정한다. `ResourceTypes`와 같은 목록이고, 고정 입력이 둘을 대조한다.
4. **답의 모양은 지금 서버 응답과 같다.**
   - 검증은 `{errors, warnings, issues: [{severity, code, processId, ioId, connectionId, message, evidence, supportedFixes, suppresses}]}`다. 순서도 같게 한다.
   - 경로 계산은 `FlowRunGraph`의 결정(보낸 연결, 양, 잃은 양, 이유)과 같다. 편집기의 "돌려 보기"는 이것을 시작 포트에서 끝까지 되풀이한다.
5. **Java가 답을 적는다.**
   - `FlowKernelFixtureTest`가 고정 입력 파일에 Java의 답을 쓰고(`-Dflow.fixtures.update=true`), 평소에는 파일과 같은지 본다.
   - 입력은 손으로 고른 그래프와 고정 시드로 만든 그래프다. 31규칙이 각각 한 번 이상 걸려야 한다. 테스트가 규칙마다 센다.
   - 경로 계산은 `FlowKernelRouteFixtureTest`가 같은 방식으로 적는다. 그래프를 발행된 판으로 읽은 결과와, 노드마다 보낸 출력의 결정이다. 결정의 이유 여덟 가지와 읽기·단계 실패가 모두 나와야 한다.
   - 그래프는 서버 응답 모양이다. 기본 경로는 `defaultRoute`(참·거짓)이고 스키마는 JSON 객체다. 편집기가 가진 것과 같다. 검증 테스트는 이것을 저장 모양으로 바꿔 넣는다.
   - Rust(`cargo test`)와 WASM(`node wasm/check-fixtures.mjs`)이 같은 파일을 맞춘다.
   - 의미를 바꾸면 Java를 먼저 고치고 답을 다시 쓴 뒤 diff를 읽고, 그다음 Rust를 맞춘다. 결정 6의 측정 전까지 Java가 정본이다.
6. **서버가 커널을 쓸지는 숫자로 정한다(4주차).**
   - 방법: Chicory(순수 Java WebAssembly 런타임, Apache-2.0)로 JVM 안에서 같은 `.wasm`을 돌린다.
   - 기준: 서버 고정 입력 전체에서 같은 답이고, 검증 한 번의 지연 중앙값과 p95가 Java의 2배 이하다.
   - 기준을 채우면 서버 검증과 경로 계산을 커널로 바꾸고, Java의 규칙 코드를 지운다. 그러면 커널이 정본이 되고 고정 입력의 답은 커널이 쓴다.
   - 채우지 못하면 Java를 정본으로 두고, 고정 입력 대조를 CI에 남긴다.
   - 어느 쪽이든 숫자를 [성능 기준선](../../operations/performance-baseline.md)에 적는다.
7. **편집기에서.**
   - 그리는 즉시 검증한다. 캔버스가 바뀔 때마다 커널을 부르고(디바운스 150ms), 이슈를 공정·포트·연결에 보인다.
   - 서버 검증은 남긴다. 발행 직전의 최종 판정이다.
   - "돌려 보기": 입력 포트에 견본 값을 넣고 커널로 경로를 끝까지 따라간다. 각 연결의 양·잃은 양·지연과 막힌 곳을 보인다. DB·발행·실행은 건드리지 않는다.
   - WASM은 편집기가 처음 그릴 때 늦게 싣는다. 크기는 CI에서 잰다. 1MB를 넘으면 줄인다.
8. **하지 않는 것.**
   - 원장·트랜잭션·권한·저장을 커널로 옮기기. 그것은 Java에 둔다.
   - 시간 시뮬레이션.
   - 협업 동기화.
   - 프런트 프레임워크 교체.

## 결과

- 좋은 점: 흐름의 의미가 한 곳에 모인다. 설계 중에 서버를 거치지 않고 결과를 본다. 돌려 보기는 실행 기록과 같은 답을 낸다. Java와 Rust의 어긋남은 고정 입력이 잡는다.
- 비용: Rust 코드가 늘고(조건식 615줄에서 수천 줄로), 고정 입력 파일과 그 생성기가 는다. 결정 6이 Java 유지로 끝나면 같은 의미가 두 언어에 남는다. 다만 고정 입력이 둘을 묶어 둔다.

## 검증

- `FlowKernelFixtureTest`: Java가 쓴 답과 파일이 같고, 31규칙이 모두 걸린다.
- `cargo test`와 `node wasm/check-fixtures.mjs`가 같은 파일을 맞춘다.
- 편집기 단위 테스트: 같은 고정 입력을 TypeScript 감싸개로 돌린다.
- 브라우저 테스트:
  - 저장 없이 이슈가 생기고 사라진다.
  - 저장 뒤 서버 검증과 같은 이슈가 나온다.
  - 돌려 보기의 결과가 같은 그래프의 서버 시뮬레이션 실행과 같다(실 API).
