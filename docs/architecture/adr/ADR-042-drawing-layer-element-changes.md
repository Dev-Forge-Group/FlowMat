# ADR-042: 그리기 층의 요소 단위 변경

작성일: 2026-11-22

## 상태

**Accepted (2026-11-22).** [월간 계획 12-21 ~ 01-15](../../status/MONTH-PLAN-2026-12-21.md) 4주차 1번이다. 세부는 2026-10-24 위임에 따라 권장안이다. 서버(결정 1~5)를 먼저 넣었고, 같은 날 편집기(결정 6)도 넣었다. 실 API 브라우저 테스트(`editor-shapes-together-real-api.spec.ts`)가 두 브라우저로 본다. 다른 도형의 이동은 둘 다 남고, 같은 도형을 옛 판에서 옮기면 늦은 쪽이 "shape-1 was changed by someone else. Their version is shown."를 본다. 이 테스트는 문서 전체 저장으로는 실패하는 것을 확인했다(두 번째 이동이 사라진다).

## 배경

- 그리기 층(편집기 문서: 도형·선·글)은 `PUT /workflows/{id}/editor-document`로 **문서 전체**를 저장한다. 요청은 `expectedVersion`(문서의 판)을 보내고, 다른 사람이 먼저 저장했으면 409를 받는다. 편집기는 그때 서버 판을 다시 보여 준다(`keepsUnsavedEdit`).
- 그래서 두 사람이 서로 다른 도형을 거의 동시에 옮기면, 늦게 저장한 쪽의 편집이 사라진다. 서버가 거절하고 편집기가 서버 판을 다시 받기 때문이다.
- 저장 방식은 이미 요소 단위다. `workflow_editor_element`가 요소마다 한 줄이고 `version`·`version_nonce`가 있다(V12). 저장이 끝나면 서버는 `EDITOR_DOCUMENT_UPDATED`를 보내고, 다른 브라우저는 문서를 다시 받는다.
- 그래프(공정·포트·연결)는 항목마다 REST로 바꾸고, 서버 검사와 발행이 그 경로에 있다. 이 ADR은 그래프를 건드리지 않는다.

## 결정

1. **요소 변경 API.** `PATCH /workflows/{workflowId}/editor-document/elements`(워크플로 쓰기 권한). 본문은 `{changes: [...], nextElementSeq?}`이고, 변경은 셋 중 하나다.
   - 추가: `{element}`(`baseVersion` 없음). 같은 id의 요소가 이미 있으면 충돌이다.
   - 바꾸기: `{element, baseVersion}`. `baseVersion`은 편집을 시작한 요소의 판이다. 지금 판과 다르거나 요소가 지워졌으면 충돌이다.
   - 지우기: `{deleteId, baseVersion}`. 지금 판과 다르면 충돌이다. 이미 없으면 그대로 둔다(같은 지우기를 다시 보내도 된다).
   - `element`의 모양과 검사는 문서 저장의 요소와 같다(`EditorElementRequest`).
2. **한 요청은 다 되거나 하나도 안 된다.** 충돌이 하나라도 있으면 아무것도 바꾸지 않고 409를 낸다. 메시지가 충돌한 요소를 이름으로 말한다(`shape-3 was changed by someone else.`). 묶기·연결선처럼 한 번에 여러 요소를 바꾸는 편집이 반만 들어가지 않게 하려는 것이다. 다른 사람이 **다른** 요소를 바꾼 것은 충돌이 아니므로, 서로 다른 요소의 편집은 둘 다 남는다. **같은** 요소는 먼저 저장한 쪽이 이기고, 늦은 쪽은 충돌로 안다.
3. **판.** 바뀐 요소마다 `version`이 1 오른다. 문서의 `version`도 요청마다 1 오른다(전체 저장과 같은 잠금 순서: 워크플로 행, 문서 행). `nextElementSeq`는 지금 값과 보낸 값 중 큰 쪽이다.
4. **알림.** 성공하면 전체 저장처럼 `EDITOR_DOCUMENT_UPDATED`를 보낸다. 다른 브라우저는 문서를 다시 받는다. 받은 문서는 끌고 있는 요소의 초안을 건드리지 않는다(초안은 편집기 쪽에 따로 있다).
5. **전체 저장은 그대로 둔다.** `PUT`은 지금처럼 `expectedVersion`으로 문서 전체를 저장한다. 편집기가 결정 6으로 옮겨 간 뒤에도, 다른 클라이언트와 되돌리기(문서 전체를 이전 판으로)는 이것을 쓴다.
6. **편집기.**
   - FlowMat의 어댑터(`editorDocumentBackendAdapter`)가 서버가 준 문서에 요소마다 판(`elementVersions`)을 붙이고, 서버가 준 문서와 화면의 초안을 구별한다(`isServerEditorDocument`). 편집기 라이브러리 사본은 고치지 않는다.
   - 저장할 때 서버가 마지막으로 준 문서와 끝난 문서를 비교해(`editorElementChanges`) 추가·바꾸기·지우기만 보낸다. 저장은 하나씩 차례로 한다. 그래서 다음 저장은 앞 저장의 답을 기준으로 삼고, 자기 편집과 충돌하지 않는다. 새 편집기 요소를 만들 때도 그 요소만 보낸다.
   - 409가 오면 서버 판을 다시 받고, 충돌한 요소의 이름을 알린다.
   - 실 API 브라우저 테스트: 두 브라우저가 다른 도형을 동시에 옮기면 둘 다 남는다. 같은 도형이면 늦은 쪽이 알림을 받는다.
7. **하지 않는 것.**
   - 필드 단위 합치기(같은 요소의 서로 다른 필드를 둘 다 남기기).
   - CRDT 라이브러리(Yjs, Automerge). 요소 판으로 서로 다른 요소의 편집이 둘 다 남고, 같은 요소는 충돌로 알린다. 그래서 지금 필요한 것은 다 된다. 필드 합치기나 오프라인 편집이 필요해지면 다시 본다.
   - 마이그레이션. 요소의 판은 V12부터 있다.

## 결과

- 좋은 점: 서로 다른 요소의 동시 편집이 사라지지 않는다. 테이블과 문서 모양은 그대로다.
- 비용: API 하나, 편집기의 비교 함수 하나가 는다. 같은 요소의 동시 편집은 여전히 한쪽이 이긴다(알림이 간다).

## 검증

- `EditorElementChangesIntegrationTest`:
  - 두 사용자가 다른 요소를 바꾸면 둘 다 남는다.
  - 같은 요소를 옛 판으로 바꾸면 409이고, 아무것도 바뀌지 않는다(같은 요청의 다른 변경도).
  - 이미 있는 id로 추가하면 409다.
  - 옛 판으로 지우면 409다. 없는 요소를 지우면 그대로 성공한다.
  - 요소와 문서의 판이 오르고, `nextElementSeq`는 큰 쪽이 된다.
  - 쓰기 권한이 없으면 403이다.
- 기존 문서 저장 테스트가 그대로 통과한다.
