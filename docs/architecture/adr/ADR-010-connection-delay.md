# ADR-010: 연결 지연(delayTimeSec) 적용

작성일: 2026-10-17

## 상태

**Accepted (2026-10-17, 사용자 결정 "Accept as recommended"). 로컬 구현 2ej(2026-10-17, 2026-10-18 `9500678`에서 커밋).** 같은 날 사용자 요청("다음작업 시작")에 따라 리드가 Proposed 초안을 썼고, 사용자가 권장안 그대로 수용 기준 8개를 닫았다. [ADR-009](ADR-009-connection-loss-rate.md)가 "결정하지 않은 것"으로 넘긴 지연(`delayTimeSec`) 적용을 정한다. 흐름률(`flowRate`)과 노드 자동 실행기는 이 ADR 밖이다.

근거: [ADR-009](ADR-009-connection-loss-rate.md) "결정하지 않은 것", [노드 실행 정책](../../domain/flow-run-execution-policy.md) EP4·EP5(재시도 대기는 `scheduledAt`으로 막음), [연결 계약](../../domain/process-port-connection-contract.md) PC-14·GR-17·GR-25·GR-33, [현재 기능](../../status/CURRENT_CAPABILITIES.md) FM-FLOW-002("지연·흐름률 미적용"), [ADR-003](ADR-003-resource-port-contract.md) 결정 5.

## 배경 (2026-10-17 코드·개발 DB 기준)

| # | 지금 동작 | 근거 |
|---|---|---|
| D1 | `process_connection.delay_time_sec`는 `numeric(10,2)`이고 기본값은 0이다(V1). 저장 검사는 절댓값 99 999 999.99 이하와 소수 2자리만 본다. 그래서 음수도 저장된다 | `ProcessConnectionServiceImpl`(`MAX_DELAY_TIME_SEC`), PC-14 |
| D2 | 실행은 지연을 읽지 않는다. 연결을 지나 만든 단계는 `scheduledAt`이 비어 있어 바로 시작할 수 있다 | `FlowRunRouter.newStep` |
| D3 | 단계의 `scheduledAt`보다 이른 `start`는 409다. 재시도 대기 단계는 `retryAt`보다 앞으로 당기는 `schedule`이 409다(EP5) | `FlowRunStepService.start`·`schedule` |
| D4 | 게이트웨이(Exclusive·Join·Split)는 서버가 system으로 바로 지나간다. 단계를 스스로 시작하는 실행기는 없다(외부가 `start`) | GR-17·GR-25·GR-33, [실행 모델](../execution-model.md) §5 |
| D5 | 발행 snapshot에 연결의 `delayTimeSec`가 이미 들어 있다. `schemaVersion`은 1(2ei 전)과 2(손실률, 2ei)다 | `WorkflowRevisionService` |
| D6 | 개발 DB(5434)에서 지연이 0이 아닌 연결은 없다 | 2026-10-17 조회 |
| D7 | 편집기에는 이미 **Delay (s)** 입력란이 있고, 실행 화면은 `scheduledAt`이 있으면 `Scheduled: …`를 보인다 | `ConnectionInspector`, `FlowRunsPanel` |

D2가 이 결정의 이유다. 건조·숙성·운반처럼 그림에 "2시간 뒤"를 적어도 실행에서는 다음 단계를 곧바로 시작할 수 있다.

## 선택지

### 1. 지연을 어떻게 지키는가

| 안 | 내용 | 좋은 점 | 약점 |
|---|---|---|---|
| A. 다음 단계의 예정 시각 | 연결을 지나 만든 단계의 `scheduledAt` = 출발 단계 완료 시각 + 지연. 그 전 `start`는 지금처럼 409(D3) | 이미 있는 규칙(D3)을 그대로 쓴다. 단계는 바로 만들어져 계획에 보인다 | 게이트웨이를 지날 때 시각을 넘겨줘야 한다 |
| B. 단계를 늦게 만들기 | 지연이 끝날 때까지 단계를 만들지 않고, 주기 작업이 때가 되면 만든다 | 실행 기록이 실제 시간 순서와 같다 | 새 대기열과 주기 작업이 필요하고, Join의 "더 올 수 있는가"(ADR-007)가 복잡해진다 |
| C. 보이기만 | 예정 시각은 안내로만 두고 `start`를 막지 않는다 | 바꿀 것이 적다 | 그림의 지연이 실행에서 지켜지지 않는다 |

### 2. 예정 시각을 앞당길 수 있는가

| 안 | 내용 | 좋은 점 | 약점 |
|---|---|---|---|
| a. 바닥 | 지연으로 정한 시각보다 앞당기는 `schedule`은 409(재시도 대기 EP5와 같다). 늦추는 것은 된다 | 물리적인 대기(건조·숙성)를 건너뛸 수 없다 | 급할 때 사람이 당길 수 없다. 그러려면 새 revision을 발행해야 한다 |
| b. 기본값 | 지연은 처음 예정 시각만 정하고 `schedule`로 자유롭게 바꾼다 | 유연하다 | 지연을 쉽게 무시할 수 있다 |

## 결정 (2026-10-17, 권장안 그대로)

1. **A(다음 단계의 예정 시각).** 새 표·열·주기 작업은 없다.
2. **기준 시각:** 출발 단계의 완료 시각(`endedAt`)이다. 출발이 게이트웨이면 게이트웨이가 받은 시각(아래 4)이다.
3. **계산:** 새 단계의 `scheduledAt` = 기준 시각 + `delayTimeSec`(소수 2자리, 마이크로초로 자름). 지연이 0이고 넘겨받은 시각도 없으면 지금처럼 비어 있다.
4. **게이트웨이:** 게이트웨이는 지금처럼 바로 지나가되, 받은 시각(들어온 연결의 기준 + 지연)을 자기 `scheduledAt`에 남기고 나가는 연결로 넘긴다. 그래서 지연은 게이트웨이를 지나며 더해진다. Join은 도착들 가운데 가장 늦은 시각을 받는다.
5. **바닥(a):** 지연으로 정한 시각보다 앞당기는 `schedule`은 409(`Step's input is ready at <시각>; schedule it at or after then.`). 늦추기·재시도 대기(EP5)는 지금과 같다.
6. **기록:** 지연으로 예정 시각을 정하면 새 단계에 `step_scheduled`(`scheduledAt`, `reason` `connection_delay`, `connectionId`, `delaySeconds`)를 남긴다.
7. **이미 발행한 revision:** 새 발행본부터. 발행 snapshot `schemaVersion`을 3으로 올리고 3 이상만 지연을 적용한다(ADR-009 결정 8과 같은 방식). 1·2는 지금처럼 지연 없이 만든다.
8. **저장·발행 검사:** 저장은 0 이상(음수 400, `numeric(10,2)` 검사는 PC-14 그대로). 발행 오류 `DELAY_RANGE`(규칙 전에 저장된 음수).
9. **화면:** 인스펙터 **Delay (s)**는 그대로 두되 0 이상만 받는다. 실행 화면의 `Scheduled: …` 옆에 `after a 2 h delay`처럼 연결 지연을 보인다.
10. **범위 밖:** 흐름률(`flowRate`)로 시간을 계산하는 것, 단계를 자동으로 시작하는 실행기, 생산 실행·작업지시 일정은 이 결정 밖이다.

## 예

- A가 09:00에 완료, A→B 지연 7 200초 → B `scheduledAt` 11:00. 10:30 `start`는 409, 11:00 뒤 `start`는 통과.
- A(09:00 완료) → 지연 1 800 → Exclusive X → 지연 3 600 → C: X는 09:00에 지나가며 09:30을 남기고, C는 10:30.
- Join: B(10:00 완료, 지연 0)와 C(10:20 완료, 지연 600)가 모이면 Join은 10:30을 받고, 뒤 단계 D(지연 0)는 10:30.
- B의 예정 시각 11:00을 10:00으로 당기는 `schedule`은 409, 12:00으로 늦추는 것은 통과.

## 수용 기준 (2026-10-17 사용자 확정)

- [x] 지키는 방식: **A 다음 단계의 예정 시각**
- [x] 기준 시각: **출발 단계 완료 시각, 게이트웨이는 받은 시각을 넘김**
- [x] Join: **가장 늦은 도착 시각**
- [x] 앞당기기: **바닥(a), 늦추기는 됨**
- [x] 기록: **`step_scheduled` reason `connection_delay`**
- [x] 이미 발행한 revision: **새 발행본부터(`schemaVersion` 3)**
- [x] 저장·발행 검사: **0 이상, `DELAY_RANGE`**
- [x] 새 마이그레이션: **없음**

## 결정하지 않은 것

- 흐름률(`flowRate`)로 처리 시간을 계산할지
- 단계를 예정 시각에 자동으로 시작하는 실행기([실행 모델](../execution-model.md) §5 "노드 자동 실행기")
- 작업자 달력·설비 가동 시간에 맞춰 예정 시각을 미루는 것(근무 시간 밖이면 다음 근무로). 설비 쪽은 [ADR-015](ADR-015-shift-aware-delay.md)에서 정했다(2026-10-18)
- 지연을 생산 실행·작업지시 일정에 넘길지

## 결과

- 좋은 점
  - 그림의 지연이 실행에서 지켜지고, 기존 `scheduledAt` 규칙과 화면을 그대로 쓴다.
  - 새 표·주기 작업 없이 된다. 이미 발행한 revision의 동작은 그대로다.
- 위험
  - 게이트웨이가 바로 지나가면서도 시각을 넘겨야 해서, 게이트웨이 단계의 `scheduledAt`은 "시작 예정"이 아니라 "받은 시각"이라는 다른 뜻이 된다.
  - 바닥(a)을 고르면 급한 경우 새 revision 발행 말고는 당길 방법이 없다.
  - 발행 snapshot 판이 셋(1·2·3)이 되어 실행 규칙이 판마다 다르다.
