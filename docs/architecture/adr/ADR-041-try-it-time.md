# ADR-041: 돌려 보기의 시간

작성일: 2026-11-21

## 상태

**Proposed (2026-11-21).** [월간 계획 12-21 ~ 01-15](../../status/MONTH-PLAN-2026-12-21.md)의 첫 결정이다. 세부는 2026-10-24 위임에 따라 권장안이다. 1주차 2번의 Java 순수 함수(`WorkingStretches`)는 2026-11-21에 먼저 넣었다(결정 3). 결정 4는 같은 날 고쳤다. 그래프 실행이 시스템 시계를 쓰므로, 실제로 돌린 시각을 고정 입력으로 쓸 수 없기 때문이다. 나머지는 계획 순서대로 한다.

## 배경

- 편집기의 "Try it"([ADR-040](ADR-040-flow-kernel.md) 결정 7)은 흐름 커널의 `walk`로 양과 경로를 따라간다. 서버가 실제로 돌린 그래프 실행 94개(`walk.json`)와 같은 답이다. 시간은 없다.
- 서버에서 단계가 언제 시작할 수 있는지는 셋이 정한다.
  - **연결 지연**([ADR-010](ADR-010-connection-delay.md)): 앞 단계가 끝난 때(게이트웨이를 지났으면 게이트웨이가 받은 때)에 지연을 더한 때가 `readyAt`이다. 합류는 도착한 것 중 가장 늦은 `readyAt`이다.
  - **근무 시간으로 세는 지연**([ADR-022](ADR-022-working-time-delay.md)): 연결의 `delayBasis`가 `working`이면, 함께 일하는 구간을 지연만큼 쌓은 때가 `readyAt`이다.
  - **근무 밖에서 기다림**([ADR-015](ADR-015-shift-aware-delay.md)·[ADR-016](ADR-016-crew-aware-delay.md)): `readyAt`이 함께 일하는 구간 밖이면 다음 구간의 시작이 `scheduledAt`이다. 게이트웨이는 받은 시각을 그대로 넘긴다.
- **함께 일하는 구간**은 생산 실행의 작업지시가 정한다. 설비의 가용 구간(달력 판, 휴일, 날짜별 교대, 정지, 프로젝트 시간대)을 구하고, 몫이 100%이고 교대가 있는 인력 각자의 근무와 겹친다. 설비도 그런 인력도 없으면 구간이 없고, 모든 시간으로 센다. 계산은 `ProductionRunWorkingTime`과 `EquipmentScheduleService.window`, 인력 달력에 있다. 7일, 31일, 366일 순으로 넓혀 찾는다.
- 이 계산을 커널에 다시 쓰면 달력과 시간대 규칙이 두 언어에 생긴다. 지난달 원칙(같은 답이 먼저, 정본은 하나)과 맞지 않는다.

## 결정

1. **커널은 구간을 받는다.** 달력, 시간대, 휴일은 계산하지 않는다. 입력은 함께 일하는 구간 `[from, until)`의 목록이다. 시각은 오프셋이 붙은 ISO 문자열(`2026-12-21T09:00:00+09:00`)이고, 빠른 것부터, 겹치지 않는다. 구간이 없으면 지금 서버처럼 모든 시간으로 센다. 구간을 정한 설비와 인력의 이름도 함께 받아, 기다린 이유를 그 이름으로 말한다.
2. **답의 모양.** 지금의 `walk` 답에 단계마다 `readyAt`(지연이 있을 때), `scheduledAt`(기다렸을 때), `held`(기다리게 한 설비와 인력)를 더한다. 시작 시각은 입력으로 받는다(편집기의 기본값은 지금). 단계는 시작할 수 있는 때 바로 끝난다고 본다. 서버의 그래프 실행에서도 단계가 보고되는 때 끝나고, 작업 시간(표준 시간)은 흐름에 없기 때문이다. 시각은 서버처럼 마이크로초로 자른다.
3. **Java의 순수 함수.** `ProductionRunWorkingTime`에서 구간만으로 정해지는 셋을 `WorkingStretches`로 뗀다.
   - `start(spans, readyAt)`: 구간 안이면 그대로(빈 답), 밖이면 다음 구간의 시작.
   - `after(spans, from, working)`: `from`부터 구간을 쌓아 `working`이 지난 때. 구간을 정확히 채우면 그 구간의 끝이다.
   - `intersect(one, other)`: 겹치는 구간.
   조회(작업지시, 인력, 설비 달력)와 7·31·366일 넓히기는 그대로 둔다. 기존 근무 시간 통합 테스트가 같은 답을 내는지로 확인한다.
4. **Java가 답을 적는다.** 그래프 실행은 시스템 시계로 단계의 끝을 적으므로, 서버에서 실제로 돌린 시각은 다시 돌리면 달라진다. 그래서 답은 두 겹으로 묶는다.
   - **순수 함수 `FlowRunSchedule`.** 라우터가 쓰는 규칙을 그대로 모은다. 끝난 때(게이트웨이는 받은 때) + 지연, 근무 시간 지연은 `WorkingStretches.afterWorking`, 합류는 가장 늦은 도착, 근무 밖이면 `WorkingStretches.firstStart`, 마이크로초로 자르기다. 고정 입력 `time.json`의 답은 이 함수가 그래프, 시작 시각, 구간, 입력에서 낸다. 사례에는 구간 안, 구간 밖에서 기다림, 근무 시간 지연이 구간 여럿에 걸침, 구간 끝에서 정확히 끝남, 구간 없음, 오프셋이 바뀌는 구간, 소수 초를 넣는다.
   - **서버와 같은지.** 통합 테스트가 생산 실행에 묶인 그래프 실행을 실제로 돌린다. 각 단계의 실제 끝 시각과 그 작업지시의 구간을 `FlowRunSchedule`에 넣어, 라우터가 적은 `readyAt`·`scheduledAt`과 같은지 본다. 시계를 고정하지 않아도 된다.
5. **구간을 내는 읽기 API.** `GET /work-orders/{id}/working-time?from=&until=`(프로젝트 읽기 권한). 함께 일하는 구간과 그 구간을 정한 설비·인력을 낸다. 기간의 기본은 7일이고 최대 366일이다. 계산은 생산 실행이 쓰는 것과 같다(`ProductionRunWorkingTime`의 조회 + `WorkingStretches`). 모자라면 편집기가 다음 기간을 다시 묻는다.
6. **편집기.** "Try it"에 작업지시 고르기를 더한다. 고르지 않으면 지금처럼 양과 경로만 따라간다. 고르면 구간을 받아 커널로 따라가고, 단계마다 시작할 수 있는 시각과 이유를 생산 단계 화면과 같은 말로 보인다(`from <날짜 시각> (waits for PRESS, kim)`). DB에는 쓰지 않는다.
7. **하지 않는 것.** 작업 시간(표준 시간), 여러 작업지시를 함께 계획하기, 자재 부족, 커널 안의 달력·시간대 계산, 서버가 커널로 시각을 정하기.

## 결과

- 좋은 점: 달력과 시간대는 Java 하나에 남는다. 커널은 구간 위의 덧셈과 비교만 하므로 작고 같은 답을 맞추기 쉽다. 편집기는 발행이나 실행 없이 흐름이 언제 끝나는지 본다.
- 비용: 읽기 API 하나, 고정 입력 파일 하나, 커널 함수 하나가 는다. 구간이 많은 기간(최대 366일)은 응답이 커질 수 있다.

## 검증

- `WorkingStretchesTest`: 손으로 계산한 사례(구간 안·밖, 구간 끝에서 정확히, 여러 구간에 걸친 근무 시간, 빈 구간, 겹침). 기존 `ShiftAwareDelayIntegrationTest`, `CrewAwareDelayIntegrationTest`, `WorkingTimeDelayIntegrationTest`가 그대로 통과한다.
- `time.json`이 Rust, WASM, TypeScript에서 모두 같다.
- 실 API 브라우저 테스트: 교대가 있는 설비와 인력의 작업지시로 흐름을 발행해 생산 실행을 돌리고, 편집기에서 같은 작업지시로 돌려 본다. 단계마다 예정 시각이 같다.
