# ADR-039: 설비별 작업지시 순서 제안(FM-AI)

작성일: 2026-11-21

## 상태

**Accepted (2026-11-21) — 1·2단계만.** 3단계(FlowMat에 넣기)는 2단계 평가에서 지금의 규칙보다 나아졌을 때만 한다. [월간 계획의 다음 달 후보](../../status/MONTH-PLAN-2026-11-16.md#다음-달-후보-11-20) 셋 중 마지막이다(compute → FM-INT-002 → FM-AI 순서, 앞의 둘은 끝남). 사용자는 "ㄱ"(계획대로 계속)으로 맡겼고, 세부는 2026-10-24 위임에 따라 권장안이다.

## 배경

- 고를 의사결정은 **설비 하나의 한 주 창에서 작업지시를 어떤 순서로 돌릴지**다. 입력은 이미 있다.
  - 전환 시간 규칙([설비 전환](../../domain/equipment-changeover.md): 품목 쌍 → 앞 품목 → 다음 품목 → 기본, [속성 규칙](../../domain/setup-attributes.md)).
  - 설비 달력·정지·시간당 산출·효율([설비 달력](../../domain/equipment-schedule.md) P1, P19).
  - 작업지시의 목표 수량, 남은 수량, 계획 시작·끝, 우선순위(urgent·high·normal·low), 상태.
- 지금의 규칙은 둘이다. 부하표의 "전환 순서 제안"(Q3: 진행 중은 고정, 8개까지는 모든 순서 중 전환 합이 가장 작은 것, 넘으면 매번 전환이 가장 작은 다음 품목, [설비 부하](../../domain/equipment-load.md))와 여러 작업지시 계획의 순서(`WorkOrderSequenceService`, 12개까지 정확히)다. 둘 다 **전환 시간만** 본다.
- **작업지시에는 납기 열이 없다.** 월간 계획 단락은 "수량과 납기"라고 적었지만, 실제로는 계획 끝(`planned_end_at`)과 우선순위만 있다. 수주(판매 주문)도 없다.
- 벤치마크 FM-AI-001~003: 제안과 실행을 나누고, 제안은 `recommendation`(입력 스냅숏, 모델·버전, 결과, 근거, 상태, 승인자)으로 남기며, 풀이기는 별도 서비스로 두되 FlowMat DB를 직접 고치지 않는다. [분리 후보](../extraction-candidates.md)는 `flowmat-ai`를 쓰기 전에 의사결정 하나와 평가 사례, 데이터를 보는 사람, 비용, 실패했을 때의 대안, 운영 책임자를 먼저 정하라고 한다.

## 결정

1. **대상과 목적.** 설비 하나, 창 하나(기본은 프로젝트 시간대의 월요일 0시부터 7일). 창 안에 계획 시작이 있는 열린 작업지시(초안·승인)를 대상으로 하고, 진행 중인 것은 맨 앞에 고정한다. 목적 함수는 **전환 분 + 늦어진 분 × 우선순위 가중치**의 합이다.
   - **늦어진 분** = max(0, 새 순서로 계산한 끝 − 스냅숏 시점의 계획 끝). 납기 열이 없으므로 사람이 정해 둔 계획 끝을 약속으로 본다. 납기 열은 이번에 만들지 않는다.
   - 가중치: urgent 4, high 2, normal 1, low 0.5. 전환 분은 1이다. 스냅숏에 적어 두므로 풀이기와 평가가 같은 값을 쓴다.
   - 끝 시각은 설비 달력의 가용 구간에 생산 시간(남은 수량 ÷ (시간당 산출 × 효율))과 앞 품목에서의 전환 시간을 차례로 채워 계산한다. 계획 P1과 같은 규칙이다. 같은 창에 다른 승인 작업지시가 차지한 시간은 가용에서 뺀다.
2. **입력 스냅숏은 FlowMat이 만든다.** `GET /equipment-load/sequence-snapshot?projectId=&equipmentId=&from=`(프로젝트 읽기 권한, 부하표와 같은 경로 아래)이 위의 입력을 JSON 하나로 낸다. 대상은 부하표 Q1과 같다. 목표 품목은 있는데 수량이 없거나 설비에 시간당 산출이 없는 작업지시는 `leftOut`에 이유와 함께 남긴다. 가용 구간은 창 시작부터 28일(`horizonEnd`)까지다. 주를 넘겨 끝나는 일도 셀 수 있게 하려는 것이다.
   - 들어가는 것: 고정·이동할 작업지시(번호, 품목, 남은 수량, 생산 분, 계획 시작·끝, 우선순위), 관련 품목 사이의 전환 분 행렬과 창 앞의 마지막 품목, 가용 구간, 가중치, 스냅숏 판(`schemaVersion`).
   - **지금 규칙의 답도 함께 넣는다.** 계획 순서와 Q3 제안 각각의 순서, 전환 분, 늦어진 분, 목적 값이다. 평가는 Java가 계산한 기준을 그대로 비교하므로, 지금 규칙을 다른 언어로 다시 짜지 않는다.
   - 스냅숏에는 품목 코드와 수량, 시각만 있다. 사람 이름, 단가, 원가는 넣지 않는다.
   - 목적 함수 계산은 Java의 순수 함수 `SequenceCost` 하나다. 순서 하나를 받아 작업지시마다 시작·끝, 전환, 늦어진 분과 합계를 낸다. 자리가 모자라면 목적 값이 없다(`unplaced`). 평가 묶음의 기준값도 같은 함수로 계산한다.
3. **풀이기와 평가는 이 저장소의 `compute/sequence-optimizer`에 둔다(2026-11-21 수정).** Python, OR-Tools CP-SAT(Apache-2.0)이다. 조건식 언어의 Rust 구현처럼 고정 입력과 Java 기준값을 한 저장소에서 함께 바꾸려는 것이다. [분리 후보](../extraction-candidates.md)의 `flowmat-ai`로 옮길지는 3단계에서 서비스로 넣기로 할 때 정한다.
   - 상태가 없는 계산이다. 스냅숏 JSON을 받아 순서와 각 작업지시의 시작·끝, 목적 값, 풀이 상태(OPTIMAL·FEASIBLE), 걸린 시간, 풀이기 판을 낸다. DB에도 FlowMat에도 쓰지 않는다.
   - 한 번 푸는 데 10초를 넘기지 않는다. 시간 안에 최적을 증명하지 못하면 찾은 가장 나은 답(FEASIBLE)을 낸다.
   - 평가 묶음은 고정 시드로 만든 스냅숏 묶음이다. 품목 수, 전환 행렬의 비대칭, 우선순위 섞임, 달력 빈틈을 바꾸며 만들고, 저장소에 커밋한다. 묶음의 지금 규칙 답은 FlowMat 백엔드 테스트가 `SequenceCost`로 다시 계산해 파일과 맞는지 본다. 조건식 언어의 고정 입력([compute](../../../compute/condition-expression/README.md))과 같은 방식이다.
   - 평가 결과는 사례마다 계획 순서, Q3 제안, 풀이기의 목적 값과 전환·늦어짐, 걸린 시간을 표로 낸다. 합계와 사례별 개선 비율도 낸다.
4. **넣을지 정하는 기준.** 평가 묶음 전체에서 풀이기의 목적 값 합이 Q3보다 **5% 이상** 작다. 그리고 Q3보다 나쁜 사례가 하나도 없다. Q3 답을 풀이기의 시작 해로 넣으므로 나빠질 수는 없다. 나빠지는 사례가 있으면 그것은 결함이다. 기준을 채우지 못하면 3단계를 하지 않고, 결과 표만 [성능 기준선](../../operations/performance-baseline.md)처럼 남긴다.
5. **3단계(조건부): 제안과 실행을 나눈다.**
   - FlowMat에 `recommendation`(종류 `work_order_sequence`, 입력 스냅숏, 풀이기와 판, 결과, 근거 = 지금 규칙과의 목적 값 차이, 상태 proposed·approved·applied·rejected·expired, 만든 사람, 승인자)을 둔다.
   - 풀이기 주소는 서버 설정 하나(`flowmat.optimizer.url`)다. 연동 프로필로 다루지 않는다. 풀이기가 없거나 시간을 넘기면 지금 규칙의 제안으로 대신하고 그렇다고 적는다.
   - 적용은 프로젝트 소유자가 승인한 뒤, 이미 있는 일정 변경 명령(`POST /work-orders/{id}/reschedules`, 사유에 추천 번호)으로만 한다. 적용 전에 스냅숏 이후 작업지시나 달력이 바뀌었으면(판 비교) 적용하지 않고 `expired`로 둔다.
6. **보는 사람.** 스냅숏과 제안은 프로젝트 구성원이 읽는다. 승인과 적용은 소유자가 한다. 일정 변경 권한과 같다.
7. **하지 않는 것.** 언어 모델, 여러 설비를 함께 푸는 일(작업 이동, 병렬 설비), 자재 부족 반영, 인력 달력 반영, 자동 적용, 납기 열 추가. 여러 설비와 자재는 이 하나가 쓸모를 보인 뒤에 다시 정한다.

## 순서

1. FlowMat: `SequenceCost`, 스냅숏 API, 평가 묶음의 지금 규칙 답을 확인하는 테스트.
2. `compute/sequence-optimizer`: 스냅숏 생성기(고정 시드)와 묶음, CP-SAT 풀이기, 평가 표. 기준(결정 4)을 채웠는지 적는다.
3. (기준을 채웠을 때) FlowMat의 `recommendation`, 풀이기 호출과 대안, 승인·적용, 부하표의 제안 화면.

## 결과

- 좋은 점: 지금 규칙과 같은 입력에서 숫자로 비교한다. 나아지지 않으면 제품에 아무것도 늘지 않는다. 풀이기는 DB를 모르므로 바꾸거나 끄기 쉽다.
- 비용: 계산 하나와 읽기 API 하나가 는다. Python 디렉터리 하나와 CI 워크플로 하나가 는다. 3단계에서는 테이블 하나, 서버 설정 하나, 서비스 운영(사용자)이 는다.

## 검증

- 1단계: `SequenceCost` 단위 테스트(손으로 계산한 사례, 가용 구간 사이에 걸치는 작업, 전환이 구간을 넘는 경우, 진행 중 고정)와 스냅숏 API 통합 테스트(권한, 창, 다른 승인 작업지시가 차지한 시간 빼기, 지금 규칙의 답이 부하표의 Q3와 같음). 평가 묶음의 지금 규칙 답을 다시 계산하는 테스트.
- 2단계: 풀이기의 답을 `SequenceCost`의 Python 거울로 다시 계산해 목적 값이 같은지 본다. 그 거울 자체도 묶음의 Java 답과 같은지 본다. 평가 표가 고정 시드에서 같은 숫자를 낸다(시간 열 제외).
